# Каталог еды на стандарт operationId

Парный документ: `megaapp-front/plans/18-food-catalogue-operation-id.implementation-plan.md`.
Источник: отложенный пункт из `17-food-diary-draft-vs-background-refresh-race.implementation-plan.md`, согласован пользователем 2026-08-02.

## Что делаем и зачем

Дневник еды и деньги (план `15`) уже несут `operationId` на каждой операции записи — сервер отличает повтор одного и того же запроса от нового по этому токену. Каталог еды (сохранить/удалить продукт) — единственные два эндпоинта в домене еды, которые этого не делают. Цель: привести под общий стандарт, без исключений по домену.

## Текущая реализация (обзор)

- `internal/food/catalogue_http.go` — `SaveProduct` (`POST /api/food/save-product`), `DeleteCatalogueEntry` (`DELETE /api/food/catalogue/{catalogueId}`) — принимают запрос, вызывают сервис напрямую, без `operationId` в теле и без обращения к `internal/platform/idempotency`.
- `internal/food/catalogue_service.go` — `SaveProduct`/`DeleteProduct` — просто пишут в БД, без транзакции идемпотентности, без версии записи.
- Следствие: повторная отправка одного и того же запроса (ретрай после таймаута, двойной клик, если бы фронт вдруг ретраил) применится **дважды** — для создания это дубль позиции в каталоге, для удаления — не страшно (второй раз просто 404), но асимметрично и не по стандарту.

## Направление

- Подключить `internal/platform/idempotency` к `SaveProduct`/`DeleteCatalogueEntry` — тем же паттерном, что уже применён к дневнику и деньгам: `operationId` обязателен в теле запроса, транзакция «проверить/применить/записать результат», повтор возвращает закэшированный результат вместо повторного применения.
- Версия записи (`ver`) каталогу не нужна — как и у дневника, версия имеет смысл только там, где есть realtime-обновление уже открытой формы поверх устаревших данных. Каталог такого сценария не имеет (правка продукта не редактируется параллельно с двух мест в реальном времени в этом приложении).

## Решено (2026-08-02) — движок дорабатывается, каталог переезжает на него полностью

Изначально здесь был открытый вопрос: `catalogue-entry-edit-form.ts` синхронно ждёт ответ сервера и показывает **конкретную** ошибку прямо в форме («уже существует» / «используется в дневнике» / «не найден»), а `SyncEngineService` умел передавать вызывающему коду только факт «не получилось», без содержания. Решение пользователя: не подстраиваться под ограничение движка, а исправить само ограничение — движок дорабатывается (различает ошибки, которые стоит повторить, от тех, что бессмысленно повторять, и передаёт содержание ошибки вызывающему коду), после чего каталог переезжает на него как положено, без урезанного варианта «только operationId, механизм синка не трогаем».

Полная механика — во фронтовом документе (там же живёт `SyncEngineService`, классификация ошибок там). Для бэкенда отдельной работы не требуется — проверил: `internal/httpx/legacy` уже несёт готовую систему типизированных ошибок (`AppError.Kind` → HTTP-статус через `ErrorStatusCodeOf`), и `catalogue_service.go` уже пользуется ей правильно:
- «already exists» → `ErrorKindValidation` → `400`;
- «used in diary entries» → `ErrorKindConflict` → `409`;
- «not found» → `ErrorKindNotFound` → `404`;
- реальные внутренние сбои (БД, генерация эмбеддингов) → `ErrorKindInternal`/`ErrorKindExternal` → `500`/`502`.

Ровно то разделение «бессмысленно повторять (4xx)» / «может пройти само (5xx)», которое нужно фронтовому классификатору — уже есть, ничего чинить не нужно.

## Затронутые флоу

| Флоу | Сейчас | После |
|---|---|---|
| Создать продукт (успех) | Применяется один раз | Не меняется |
| Создать продукт, таймаут/обрыв, повтор с тем же `operationId` | Может создать вторую позицию в каталоге | Возвращает закэшированный результат первой попытки, дубля не будет |
| Удалить продукт | Применяется один раз | Не меняется |
| Удалить продукт, повтор с тем же `operationId` после того, как удаление уже прошло | Вернул бы 404 «не найден» — сбивает с толку при повторной отправке того же запроса | Возвращает тот же успешный результат («удалено»), а не 404 — тот же принцип, что уже есть у `DeleteDiaryEntry`/`DeleteTransaction` |
| Ошибка «уже существует» / «используется в дневнике» / «не найден» | Показывается в форме | Не меняется — текст и статус те же, только теперь ещё и защищены идемпотентностью |

## Реализовано (2026-08-02)

- `catalogue_repo.go` — `CreateCatalogueEntry`/`UpdateCatalogueEntry`/`DeleteCatalogueEntry` переведены на явную `*sql.Tx` вместо прямого `r.write` (тот же стиль, что уже у диаграммы дневника в `write_repo.go`).
- `catalogue_service.go` — добавлен `peekIdempotency` (копия паттерна из `internal/money/service.go`: короткая транзакция только на проверку, закрывается сразу, не держится на время генерации эмбеддингов). `SaveProduct`/`DeleteProduct` — новая сигнатура `(ctx, userID, operationID, ...)`, возвращают `(result, applied, err)`. Идемпотентность кэширует только id результата (не весь объект) — на повторе и на свежем применении финальный `*CatalogueEntry` собирается одним и тем же путём (`s.GetCatalogueEntry`), без дублирования логики сборки.
- `catalogue_http.go` — оба хендлера требуют `operationId` (400 без него), `DeleteCatalogueEntry` теперь тоже читает тело запроса и claims пользователя (раньше не делал ни того, ни другого). Realtime-рассылка и инкремент метрики — только при `applied` (не при повторе).
- Попутно поправлено: HTTP-хендлер отдавал `"Product not found"` (с большой буквы) в редком гоночном случае (запись удалена конкурентно между проверкой и удалением), а сервисный слой в обычном случае — `"product not found"` (с маленькой). Фронту пришлось бы сравнивать с двумя вариантами регистра одного и того же сообщения — выровнено на нижний регистр, как везде в остальных сообщениях сервиса.
- Тесты: `TestSearchPreviewAndSaveProduct` обновлён под новую сигнатуру; добавлены `TestSaveProductSameOperationIDReplaysWithoutDuplicate`, `TestDeleteProductRetrySucceedsInsteadOfNotFound`. `TestFoodSearchAndCatalogueMutationEndpoints` (HTTP-уровень) обновлён — `operationId` в теле POST/DELETE. `go build`/`go vet`/`go test ./...` — все зелёные.
