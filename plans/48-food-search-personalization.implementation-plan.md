# 48. Персонализация поиска еды по истории выборов — бэкенд (основной план)

Парный план фронтенда: [48-food-search-personalization.implementation-plan.md](../../megaapp-front/plans/48-food-search-personalization.implementation-plan.md).

Продолжает «Идеи на будущее» плана [43](43-food-search-ranking.implementation-plan.md): там переранжирование по частоте было отложено «до замера». Теперь решено делать, но по более точному сигналу — не «что ем вообще», а «что выбираю по этому запросу».

## Цель

Поиск учится на выборах конкретного пользователя. «Конфеты» → всегда ем леденцы → леденцы первые. «Молоко» → 80% 2,5%, 17% 3,2%, 3% 6,5% → именно в этом порядке. Сменились привычки → за разумное время выдача перестраивается. Векторный поиск и текстовое повышение остаются основой; личная история — отдельная добавка поверх, сильная настолько, чтобы привычный товар шёл первым.

## Как сейчас

- Поиск не знает пользователя: `userId` до ранжирования не доходит.
- Ранжирование: сходство вектора запроса с векторами товара + 0,25 за каждое слово запроса, начинающее слово названия; выдача — 30 лучших, ничья по алфавиту.
- Снимок индекса в памяти (товары, векторы) + кэш готовых выдач по запросам внутри снимка; кэш пользователю не принадлежит. Кэш только для области «активные».
- Создание записи дневника — одна транзакция с идемпотентностью по `operationId`. Запроса, по которому товар найден, сервер не получает.
- Откат/повтор операции безопасен: повтор по `operationId` отдаёт сохранённый результат и ничего не пишет.

## Ключевые решения

### 1. Что считается выбором
- Выбор = создание записи дневника с товаром, найденным поиском. Не клик по карточке: клик ещё не «съел», пользователь может вернуться, открыть правку, передумать.
- Фронт присылает текст запроса вместе с созданием записи (необязательное поле тела). Сервер пишет выбор **в той же транзакции**, что и запись дневника.
- Следствия: ровно один раз (повтор по `operationId` ничего не добавляет); нет рассинхрона «запись есть, выбора нет»; отдельного канала и новой очереди не нужно.
- Выбором не считаются: восстановление удалённого дня, выбор товара для истории продукта, создание нового товара «на лету» (отложено, см. ниже), легаси-поиск.
- Удаление записи выбор не отменяет: поиск привёл к товару, это факт.

### 2. Хранение: журнал выборов, не счётчики
- Новая таблица: пользователь, нормализованный запрос, товар, время выбора. Одна строка на выбор. Миграция — новая (последняя 000014 уже выкачена).
- Индекс по пользователю и запросу, покрывающий товар и время: чтение — диапазон по префиксу, без обращения к таблице.
- Почему журнал, а не накопленные «затухающие счётчики»: затухание считается при чтении, поэтому период забывания можно менять без пересчёта данных; видно, что и когда выбирал; запись — простой INSERT без «прочитать-изменить-записать».
- Объём: порядка 10 тысяч строк в год на пользователя — мегабайт; чистка не нужна. Строки устаревших товаров безвредны: индекс их просто не знает.
- История строго по пользователю: чужие выборы на выдачу не влияют.

### 3. Ключ запроса
- Тот же текст, что ушёл в поиск (раскладка уже исправлена фронтом, вес «200 г» отрезан), в нижнем регистре, ё→е, пробелы схлопнуты.
- Пустой, слишком длинный (>100 символов) или отсутствующий запрос — выбор не пишется, запись дневника сохраняется как обычно. Это подсказка, а не данные дневника: ошибкой не считается.

### 4. Какие прошлые выборы относятся к текущему запросу
Пользователь набирает по буквам и нажимает на товар, как только видит его — на «конф», на «конфет», на «конфеты». Если считать только точное совпадение ключа, опыт дробится по длине набора и первые буквы никогда не получают подсказку.

- Выбор по запросу K относится к текущему запросу Q, если K начинается с Q (в том числе K = Q). Это диапазон по префиксу в индексе.
- Вес: доля набранного, «длина Q / длина K» в символах. «конфеты» при наборе «конф» — 0,57; «конфет» — 0,86; полный — 1. Чем дальше до привычного запроса, тем слабее подсказка.
- Обратное направление (Q длиннее K, например «конфеты» после выбора по «ко») не учитывается: выбор по короткому запросу двусмыслен («ко» → кофе), а длинный запрос уточняет намерение.
- Стемминг ключей не применяется: набор по буквам он ломает, а форма слова у человека обычно постоянна.

### 5. Затухание: период полураспада 30 дней
Вес выбора = 0,5 в степени (возраст в днях / 30). Не по дням и не по месяцам-корзинам, а непрерывно: нет границ, на которых выдача скачет.

- Смысл числа: при неизменной частоте покупок новый товар догоняет старый ровно через период полураспада. Вышел из 2,5% на 3,2%: через 15 дней доля 3,2% — 29%, через 30 — 50% (порядок меняется), через 60 — 75%, через 90 — 88%.
- Все товары одного запроса затухают одинаково. Если запрос полгода не вводили, соотношение между товарами сохраняется, падает только общая уверенность (см. ниже).
- 30 дней — константа в одном месте, подбирается без миграции данных.

### 6. Бонус товара
Для текущего запроса суммируем веса выборов по каждому товару (с учётом затухания и доли набранного). Пусть сумма по товару — масса, сумма по всем товарам — всего.

- Доля = масса товара / всего.
- Уверенность = всего / (всего + 1). Один свежий выбор — 0,5; три — 0,75; десять — 0,91. Устаревший единичный выбор тает: через 30 дней 0,33, через 90 — 0,11, через полгода — почти ноль. Отдельных порогов «забыть» нет — всё плавно.
- Бонус = 2 × доля × уверенность. Добавляется к обычной оценке (сходство + повышение за слова).
- Свойства:
  - Привычный товар (доля ≥ 0,8) получает 1,5–2 — больше любой реальной разницы между лучшим и четвёртым по вектору. Леденцы идут первыми.
  - Один выбор уже даёт ~1,0, то есть поднимает товар сразу, на следующем же поиске.
  - «Молоко»: доли 0,8 / 0,17 / 0,03 при уверенности ~0,95 дают бонусы 1,5 / 0,32 / 0,06 — порядок 2,5% → 3,2% → 6,5% → остальные по вектору; единичный случайный выбор (доля 5%) почти ничего не меняет.
  - Вектор не выбрасывается: непривычный товар с высокой близостью всё ещё может обойти редко выбираемый.
- Если в запросе два привычных товара, они идут друг за другом по долям, оба выше непривычных.

### 7. Кандидаты
Товар с положительным бонусом всегда кандидат — даже без совпадения слов и с неположительным сходством. Иначе привычный товар, не найденный по короткому префиксу, не показался бы. Область (активные/архив/все) применяется как прежде.

### 8. Поиск в два этапа и кэш
- Этап 1, не зависит от пользователя: базовая оценка каждого товара снимка (сходство + повышение за слова) и признак кандидата. Кэшируется по запросу внутри снимка, как кэш выдач сейчас. Теперь кэш годится для любой области, а не только «активных»: область применяется на этапе 2.
- Этап 2, зависит от пользователя, считается на каждый запрос: прочитать выборы по префиксу → бонусы → сумма → сортировка → 30 лучших. Это один индексный запрос в SQLite и ~450 сложений.
- Кэш остаётся общим, ключ пользователя в нём не нужен, инвалидировать при выборе нечего: новый выбор виден со следующего запроса автоматически.
- Память кэша: ~4 КБ на запрос; сбрасывается при каждом изменении каталога и рестарте. Приемлемо.
- Как и сейчас: без вектора запроса (сбой OpenAI) этап 1 не кэшируется; личный бонус при этом работает — как раз выручает.
- Сбой чтения выборов — ошибка поиска (по принципу плана 43: сбой БД не маскируется).
- HTTP-маршрут поиска тоже получает пользователя из токена и идёт тем же путём.

### 9. Контракт с фронтом
- В теле создания записи дневника — необязательное поле с текстом запроса. Нет поля — выбор не пишется. Совместимо в обе стороны: старый фронт его не шлёт, старый бэк новое поле игнорирует (строгого разбора лишних полей нет).
- Описание API (openapi) дополняется.
- Протокол WebSocket поиска не меняется.

## Что сознательно не делаем

- Не «первое место навсегда»: ни жёсткого выбора единственного товара, ни отключения вектора. Бонус добавка, не замена.
- Не отрицательный сигнал («показали, но не выбрал»): доли и так вытесняют соседей, а «показали» — шумный сигнал.
- Не поправка на позицию (клик по первому ради Enter): выбор по Enter — тоже явное подтверждение; выдача сама сменится, когда пользователь начнёт выбирать другое.
- Не учёт слов по отдельности («белый» + «хлеб»): цельный запрос точнее и проще, примеры пользователя — однословные.
- Не общий приор «часто ем» из дневника (см. идеи).
- Не создание нового товара как выбор (запрос «ничего не нашёл» → создал → съел): редкий случай, добавить можно позже.
- Не периодическая чистка журнала.

## Идеи на будущее

- **Приор из дневника.** Холодный старт: у пользователя 5 лет записей, но без запросов. Слабый (до ~0,1) бонус по частоте и свежести товара в дневнике помогал бы с первого дня и при новых запросах. Возвращаться, если через 2–3 недели после выкладки привычные продукты по новым запросам всё ещё плохо ранжируются. Бонус по частоте обязан быть слабым, иначе «часто ем хлеб» будет подниматься по запросу «конфеты».
- **Позиция выбора.** Если окажется, что выбор по Enter закрепляет первое место навсегда, учитывать позицию выбранного (клик по четвёртому — сильнее сигнал, чем Enter по первому).
- **Подбор параметров** (период полураспада, множитель 2, константа уверенности 1) по накопленным выборам: метрика — средняя позиция выбранного товара.

## Параметры и калибровка

Начальные значения: полураспад 30 дней, множитель бонуса 2, константа уверенности 1. Данных о запросах-выборах нет — они начнут копиться только после выкладки фронта. Поэтому:

- Множитель проверяется на регрессионном наборе с копией боевой БД: максимальный разрыв между первой и тридцатой базовой оценкой по популярным запросам. Бонус одного свежего выбора (0,5 × множитель) должен его перекрывать с запасом, иначе множитель растёт.
- Поведение зафиксировано сценарными тестами (привычка, смена привычки, забывание, префикс), а не магическими числами: если константы меняются, смысл тестов не должен.
- Реальные значения подбираются после выкладки по метрике фронта (позиция выбранного товара).

## Риски

- **Самоподкрепление.** Привычный товар первый → чаще выбирается → ещё сильнее. Лечится затуханием: пока пользователь выбирает другое, доля меняется. Бонус не отключает вектор.
- **Случайный выбор.** Один раз выбранное «по ошибке» поднимает товар немедленно (доля 100%). Смягчение — уверенность и следующий нормальный выбор: доля перераспределится.
- **Короткие префиксы** (1–2 буквы). Работают как автодополнение по привычкам; вес доли набранного делает вклад слабым. Если окажется шумно — минимальная длина запроса для личного бонуса.
- **Мерцание клиентского кэша.** Фронт показывает сохранённый порядок и меняет его на ответ сервера — после выбора порядок может поменяться один раз. Устраивает, см. парный план.
- **Мульти-пользователь.** Таблица и чтение строго по пользователю; тест на изоляцию.

## Проверка

Автоматические, табличные:

- Чистая математика бонусов: затухание (полураспад), доля набранного, нормировка в доли, уверенность; пустая история; нулевая сумма после очень долгого срока (деление на ноль).
- Сценарии: «молоко» 80/17/3; смена привычки (когда порядок меняется); забывание единичного выбора; префиксы «конф» → «конфеты»; обратное направление не работает; стемминг не применяется; ё/регистр/пробелы.
- Ранжирование: бонус перекрывает разрыв базовых оценок; кандидат без слов и с нулевым сходством, но с бонусом, попадает в выдачу; область соблюдается; ничья по алфавиту; без вектора запроса личный бонус работает.
- Запись выбора: в одной транзакции с записью дневника; повтор по `operationId` строку не добавляет; пустой/слишком длинный запрос — запись создаётся, выбор нет; восстановление дня выборов не пишет; архивный товар — запись отклонена, выбор не записан.
- Сервис: два пользователя с разными привычками получают разный порядок при одном запросе; новый выбор виден со следующего поиска без сброса; кэш этапа 1 общий.
- Миграция применяется на чистой базе (существующий тест миграций).
- Регрессионный набор на копии боевой БД: прежняя точность без личной истории не изменилась (бонус нулевой); с моделируемой историей по реальным запросам привычный товар первый; замер разрыва для множителя.
- Сборка, `go vet`, `go test ./...` зелёные.

## Уточнение: связь запросов в обе стороны (30.10.2026)

Заменяет в разделе 4 абзац «Обратное направление не учитывается». Причина: человек нажимает на товар на разной длине набора. Выбор, сделанный на «конфет», не поддерживал бы «конфеты», и при добавлении одной буквы карточки резко перестроились бы.

- Запросы связаны, если один является началом другого, в любую сторону. Вес связи = длина короткого / длина длинного (в символах).
- «конфет» и «конфеты» — 0,86: почти то же самое. «конфеты» при наборе «конф» — 0,57. «ко» и «конфеты» — 0,29: слабая связь.
- Один свежий выбор при связи 0,86 даёт бонус ~0,9 (масса 0,86, уверенность 0,46): ниже полного (1,0), но всё равно выше типичного разрыва по вектору. Это и есть «чуть слабее, чем при точном совпадении, но высоко».
- Короткий старый запрос слабо влияет на длинный. Точные выборы по длинному запросу доминируют по доле, поэтому «ко» → кофе не мешает «конфеты» → леденцы.
- Новый выбор на «конфет» пишется отдельной строкой под «конфет». Следующий ввод «конфет» — точное совпадение с полным весом.
- Чтение: диапазон по префиксу (сохранённые запросы, начинающиеся с набранного) плюс точечные поиски по всем началам набранного (сохранённые запросы, являющиеся началом набранного). Это не больше N+1 индексных запросов, N — длина запроса; можно одним запросом со списком.
- Стемминг по-прежнему не применяется. «конина» и «конфеты» не связаны (ни один не начало другого): на наборе «кон» подсказка есть (вес 0,43), на «кони» уже нет.
- Что стирание не отслеживается и не нужно: в журнал попадает только текст поля в момент выбора. «пиво» → стёр → «конфеты» не связывает «пиво» с выбранным товаром.

### Чеклист уточнения

- ✅ Вес связи = короткий / длинный, обе стороны в одной формуле
- ✅ Тесты: «конфет» ↔ «конфеты» в обе стороны; «ко» слабо влияет на «конфеты»; «пиво» не получает выбор «конфеты»; новый выбор на «конфет» даёт полный вес при повторе

Причина: хвост старше определённого срока ничего не весит из-за затухания, хранить его незачем; перестал выбирать — перестал есть, при возвращении история копится заново (одного выбора хватает, чтобы товар поднялся).

### Баги
1. Очень длинный запрос раздувает память и ломает поиск
   - **Класс:** B
   - **Важность:** стоит поправить
   - **Как сейчас работает:** для каждого поиска сервер ищет сохранённые выборы по запросам, которые являются началом набранного текста. Для этого он нарезает набранный текст на все его начала и передаёт каждое отдельным параметром в запрос к базе. Сохраняются только запросы до 100 символов, но длину набранного текста при поиске никто не ограничивает: сокет принимает сообщение до 64 КБ.
   - **Что не так:** запрос в 30–60 тысяч символов (случайная вставка большого текста или умышленная отправка залогиненным пользователем) даёт десятки тысяч начал общей длиной в сотни миллионов символов. Это сотни мегабайт, а то и гигабайт памяти на один поиск, после чего база отвечает «слишком много параметров» (предел около 32 тысяч), и поиск по такому запросу падает ошибкой. До персонализации такой запрос просто искался по названиям. Нарезка начал при этом не нужна: ни один сохранённый запрос длиннее 100 символов быть не может, и выбор по обрывку такого текста ничего не значит.
   - **Как поправить:** для запроса длиннее предела хранимых запросов личную историю не читать вовсе (бонусов нет). Одна проверка длины в месте, где читаются связанные выборы.
   - **Как будет работать после правки:** длинный запрос ищется по названиям и вектору, как раньше; память и число параметров не зависят от длины текста.
   - **Объём правки:** малый — одно условие в чтении личных бонусов плюс тест на запрос длиннее предела.
   - **Рекомендация:** чинить — класс B, стоит поправить, правка малая.

2. Метрика «позиция выбранного товара» шумит
   - **Класс:** B
   - **Важность:** мелочь, но стоит поправить
   - **Как сейчас работает:** (фронт) событие `food.catalogue_pick` пишется при каждом выборе из выдачи; время считается от последнего показа списка.
   - **Что не так:** то же поле поиска служит для выбора продукта под историю продукта, там это событие пишется тоже, хотя запись дневника не создаётся, и размывает метрику, ради которой оно заведено. Если ответ сервера перестроил показанный список, время «до выбора» отсчитывается заново. Для товара, которого уже нет в показанной выдаче, позиция равна 0.
   - **Как поправить:** писать событие только на пути добавления в дневник (его знает `FoodSearch`, а не служба поиска) и считать время от первого показа списка этого запроса; не писать событие при отсутствии товара в выдаче.
   - **Как будет работать после правки:** метрика отражает только выбор для дневника.
   - **Объём правки:** средний — разнести подсчёт позиции и запись события между службой поиска и `FoodSearch`, поправить тесты.
   - **Рекомендация:** не чинить — класс B, мелочь, правка средняя: метрика вспомогательная, для подбора параметров хватает того, что есть.

**Замечено рядом (не блокирует):** (1) при большой истории уверенность насыщается, поэтому выбор по длинному запросу сильно влияет и на его короткое начало («м» поднимает самое частое «м…»): вклад близости виден только при малой истории; поведение похоже на автодополнение по привычкам и, скорее всего, желательно, но противоречит фразе плана «вклад слабый». (2) В пакете `food` свои `min` и `max` только для `int` затеняют встроенные (service.go).
