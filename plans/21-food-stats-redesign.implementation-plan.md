## Что делаем и зачем

Фронт встраивает 5 новых карточек статистики в дневник еды (парный документ). Из них 4 (лента-30-дней, streak, "год назад"/личные рекорды, часть итогов пути) считаются **полностью на клиенте** — `GET /api/food/stats` уже отдаёт всю историю пользователя целиком (от первой даты до сегодня включительно) при каждом вызове, ничего нового возить не нужно.

Не хватает ровно двух вещей: вклада продуктов в калораж (карточка "топ-продукты") и точного числа записей дневника за всё время (часть карточки "итоги пути"). **Решение — расширить ответ существующего** `GET /api/food/stats`, не заводить отдельный эндпоинт: фронт и так дёргает именно этот эндпоинт на каждой загрузке страницы, а данные для обеих недостающих вещей уже загружаются и обходятся внутри существующего `Service.GetStats` — просто не сохраняются наружу:

- `GetStats` уже грузит вообще все записи дневника пользователя (`GetStatsDiaryHistory`, диапазон от самой первой записи пользователя до сегодня) — отдельный запрос "записи за диапазон" не нужен, диапазон и так максимальный.
- Внутри уже существующего цикла по дням (`service.go:759-767`) каждая запись дневника уже резолвится в ккал через `PersonalKcalResolver.AppliedKcal(row.FoodCatalogueID, yearMonth)` — вклад по продуктам получается побочным аккумулятором в этом же цикле, без нового запроса к БД или к резолверу.
- `len(diaryRows)` (уже загруженный слайс) — это и есть точное число записей дневника за всё время, без отдельного `COUNT(*)`.
- В `foodDiary` `del` — не soft-delete флаг, реальное удаление записи — `DELETE FROM foodDiary` (`write_repo.go:90`), колонка `del` нигде не используется как фильтр, фильтровать по ней не нужно.

Отдельный эндпоинт означал бы два HTTP-запроса на одну загрузку страницы вместо одного, два места с похожей логикой резолвинга ккал вместо одного и риск рассинхрона суммы топ-продуктов с `ConsumedKcal` при любом будущем изменении резолвера — расширение существующего ответа проще и надёжнее по всем трём пунктам.

## Текущая реализация (обзор)

- `GET /api/food/stats` → `internal/food/http.go:107` (`Handler.GetStats`) → `service.go:727` (`Service.GetStats`) — без query-параметров: строит полный список дат от `GetUserFirstDate` до сегодня включительно, тянет всю историю веса и дневника, гоняет через `PersonalKcalResolver`, кэширует в памяти (`stats_cache.go`, инвалидация на любую запись в дневник/вес).
- `DayStats` (`service.go:84`): `{Weight, WeightAvg, ConsumedKcal, TargetKcal, IsVirtualKcalDay}`. Побочное наблюдение: `IsVirtualKcalDay` (`service.go:766`) захардкожено `false` в единственном месте, где `DayStats` собирается — фактически мёртвое поле уже сейчас. Не трогаем, вне scope этого плана.
- `buildPersonalKcalResolver` (`service.go:141`) уже грузит `s.repo.GetCatalogue(ctx)` целиком (id→kcal-калорийность на 100г) для резолвера — те же строки несут `Name`, просто сейчас не сохраняются в возвращаемую карту.
- Таблицы: `foodDiary(id, dateISO, foodCatalogueId, foodWeight, history, usersId, ver, del)`, `foodCatalogue(id, name, kcals, ...)`.

## Новый контракт `GET /api/food/stats`

Ответ меняется с плоской карты дней на объект:

```
{
  days: { "<dateISO>": DayStats, ... },   // то же самое содержимое, что и сейчас, просто под ключом — по сегодняшний день включительно
  topProducts: [ { catalogueId, name, kcal }, ... ],  // топ-5 продуктов по вкладу в ккал за последние 30 дней (включая сегодня)
  totalEntries: number                    // всего записей дневника за всё время
}
```

- Окно для топ-продуктов — фиксированные последние 30 завершённых дней, **не включая сегодня** (решено вместе с пользователем: сегодняшний день не завершён, лента-30-дней и streak на фронте тоже его не учитывают), без query-параметра диапазона. Совпадает с окном ленты-30-дней на фронте — обе карточки говорят об одном и том же периоде. Карточки для непосвящённых пользователей не должны требовать выбора диапазона — это удел старого технического графика с слайдером.
- `share`/проценты — не отдаётся с бэка: фронт и так получает `days` (полную историю) в том же ответе, сумма `consumedKcal` за то же 30-дневное окно уже доступна на клиенте — процент вклада продукта считается на фронте делением, без дублирования одной и той же арифметики на двух сторонах.
- Топ-N — константа 5 (вариант A из концепта), захардкожена в коде, без query-параметра.

## Реализация

- `buildPersonalKcalResolver` — дополнительно возвращает `catalogueNameByID map[int64]string` (те же строки `s.repo.GetCatalogue`, которые уже читаются для `catalogueKcals`, просто дополнительно сохранить `Name`).
- `Service.GetStats` — тип возврата меняется с `map[string]DayStats` на новый `StatsResponse{ Days map[string]DayStats; TopProducts []ProductStat; TotalEntries int }` (JSON: `days`/`topProducts`/`totalEntries`); `ProductStat{ CatalogueID int64; Name string; Kcal float64 }` (JSON: `catalogueId`/`name`/`kcal`). Граница диапазона (`lastDate`) — без изменений, по сегодняшний день включительно.
- Внутри существующего цикла по `allDates` (`service.go:759`) — рядом с накоплением `consumed` добавить накопление в `productKcal map[int64]float64`, но только для записей, где `date` внутри последних 30 дней от `lastDate` (простое сравнение строк ISO-дат, дата хронологически сортируема как строка).
- После цикла — отсортировать `productKcal` по убыванию, взять первые 5, подставить имена из `catalogueNameByID`, собрать `[]ProductStat`.
- `totalEntries := len(diaryRows)` (уже загруженный слайс `GetStatsDiaryHistory`) — без дополнительного запроса.
- `stats_cache.go` — тип кэша меняется с `map[int64]map[string]DayStats` на `map[int64]StatsResponse`; инвалидация (на любую запись дневника/веса) не меняется — тот же триггер корректно сбрасывает и новые поля.
- `http.go` (`Handler.GetStats`) — логика не меняется, просто сериализует новый тип ответа.
- Изменений схемы/миграций не требуется.

## Решённый вопрос

Streak/лента-30-дней (на фронте) сегодняшний день не учитывают — решено с пользователем. `days` по-прежнему несёт все дни по сегодняшний включительно (фронт сам решает, использовать ли последний день); окно топ-продуктов на бэке приведено в соответствие (см. выше).
