# 32. Scope-based доступ к `/metrics`: бэковая часть

Часть общего рефакторинга `/metrics` (мегаapp-front план [32-metrics-mobile-custom-only-mode.implementation-plan.md](../../megaapp-front/plans/32-metrics-mobile-custom-only-mode.implementation-plan.md), Flatline-часть — [flatline/plans/06-metrics-history-scope-filter.implementation-plan.md](../../../flatline/plans/06-metrics-history-scope-filter.implementation-plan.md)). Этот документ — только то, что меняется в мегабэке.

## 1. Задача

Браузер должен уметь подписаться (WS) и запросить историю (REST) не на все метрики всех сервисов, а на список `(service, metricName)`, соответствующий тому, что реально открыто на странице `/metrics`. Мегабэк — прозрачный посредник между авторизованным браузером и Flatline (труба, см. предыдущий разбор), поэтому здесь только проброс scope и его применение к рассылке, без собственной бизнес-логики метрик.

## 2. Текущее состояние (для справки)

- `HistoryHandler.History` ([http.go:29](../internal/metrics/http.go:29)) — принимает только `minuteSince/hourSince/daySince`, зовёт `FlatlineClient.History` без фильтра.
- WS `METRICS_SUBSCRIBE` ([ws_handlers.go:9](../internal/metrics/ws_handlers.go:9)) — без payload.
- `Realtime.subscribers` ([realtime.go:23-27](../internal/metrics/realtime.go:23)) — плоский `map[*ws.Client]struct{}`, `BroadcastDetail` ([realtime.go:41](../internal/metrics/realtime.go:41)) шлёт всем подписчикам одно и то же сообщение без фильтрации.
- `Poller.tick` ([poller.go:85](../internal/metrics/poller.go:85)) — фоново, раз в интервал, тянет у Flatline **всё** через `client.Since(...)` ([poller.go:92](../internal/metrics/poller.go:92)), рассылает `BroadcastDetail` подписчикам и `BroadcastLatest` всем админам.

## 3. Что меняется

### 3.1. REST `/api/metrics/history`

Принимает список scope-элементов `{service, metricNames: []string}` — тот же контракт, что определён во Flatline-плане §2.1: `metricNames` всегда непуст, без wildcard-режима («весь сервис» не поддерживается нигде в этой цепочке — если метрика не в каталоге фронта, её просто не запрашивают, см. фронтовый план §4.1). Мегабэк **не трансформирует** этот список — валидирует форму (непустой список, у каждого элемента непустой `metricNames`, разумный размер) и передаёт как есть в `FlatlineClient.History` → Flatline. Один и тот же контракт по обе стороны мегабэка — меньше форматов для поддержки, меньше места для рассинхрона при будущих правках.

Без scope в запросе — 400, не «дай всё по умолчанию». Легаси-режима «без scope = всё» не вводим: единственный потребитель этого REST-эндпоинта — сам фронт этого же приложения, обновляется тем же релизным циклом, скрытых внешних потребителей нет.

### 3.2. WS `METRICS_SUBSCRIBE`

Payload получает тот же список scope-элементов. `NewSubscribeHandler` ([ws_handlers.go:9](../internal/metrics/ws_handlers.go:9)) после проверки `IsAdmin` зовёт `realtime.Subscribe(client, scope)` — новая версия, не `Subscribe(client)`.

Повторный `METRICS_SUBSCRIBE` от того же клиента (переключение раздела на фронте) **заменяет** его scope целиком, не объединяет со старым — иначе клиент со временем накопит подписку на всё, что когда-либо открывал за сессию, и весь смысл scoping'а потеряется.

`METRICS_UNSUBSCRIBE` — без изменений, просто убирает клиента из карты целиком.

### 3.3. `Realtime` — per-client scope

`subscribers map[*ws.Client]struct{}` → `subscribers map[*ws.Client]scope` (тот же маленький тип, что описан в §2.1 Flatline-плана, локальная копия в этом репозитории — эти два сервиса не шарят Go-код между собой, только формат сообщений; ровно тот же принцип, что уже принят в проекте для producer'ов, см. `flatline/plans/00-FLATLINE-ARCHITECTURE.design-doc.md` §3.3a — «копируется архитектура, не код»).

`BroadcastDetail` — вместо одного сообщения всем, для каждого подписчика фильтрует входящие `Points` по его scope (простая проверка «пара (service, metricName) есть в scope клиента») и шлёт только совпавшее; если после фильтрации пусто — не шлёт вообще ничего этому клиенту на этом тике. Дешёвая проверка (map lookup на точку на клиента), тиков с большим числом новых точек за раз не бывает (`Poller` и так уже дедуплицирует «уже виденное» до рассылки, см. [poller.go:109-119](../internal/metrics/poller.go:109)).

### 3.4. Что НЕ меняется — и почему

- **`Poller.tick`** — продолжает опрашивать Flatline **полностью**, без scope. Это один фоновый процесс на всё приложение, а не по процессу на клиента — если бы он сам сужался под чей-то scope, при нескольких одновременно смотрящих клиентах с разными scope пришлось бы либо гонять несколько параллельных опросов (дороже, чем сейчас), либо объединять их scope в один (тогда это снова «почти всё», просто через дополнительный слой). Плюс `BroadcastLatest`/health-сводка нужна независимо от того, что сейчас открыто у кого-либо — она всё равно требует полных данных по всем сервисам. Сужать нечего и незачем.
- **`BroadcastLatest`/health-канал** — без изменений, всем админам, всегда, все сервисы. Severity-индикаторы должны быть видны и для сервисов, свёрнутых в хедере — то есть заведомо вне scope открытой сейчас панели.
- **Авторизация** — не трогаем. `auth.Middleware`/`IsAdmin` как были на входе в REST и на входе в WS-подписку, так и остаются; Flatline как был без пользовательской авторизации (IP-allowlist), так и остаётся. Мегабэк — единственная точка, где проверяется личность конкретного пользователя, это не пересматриваем (см. разбор «труба vs напрямую» — труба остаётся).
- **Версионирование WS-протокола на время раскатки** (старый фронт — новый бэк или наоборот): не строим отдельный legacy-режим. Однопользовательское приложение, деплой фронта и бэка занимает секунды, а не часы; худший случай — несколько секунд пустой/неполный дашборд до реконнекта или обновления страницы, самовосстанавливается без вмешательства. Специальный compat-код здесь — сложность ради риска, которого по факту нет.

## 4. Чеклист

- ✅ REST `/api/metrics/history`: стал `POST` с JSON-телом `{minuteSince, hourSince, daySince, scope}` (scope не укладывался в query-string), валидация (непустой список, у каждого элемента непустой `metricNames`), 400 без scope. (Числовой предел `maxScopeMetrics=200` был здесь изначально, позже убран — см. пункт ниже.)
- ✅ `FlatlineClient.History`: передаёт scope в запрос к Flatline без трансформации (POST JSON, тот же контракт).
- ✅ WS `METRICS_SUBSCRIBE`: payload со scope (`{payload: {scope: [...]}}`), `IsAdmin`-проверка как была; невалидный scope от уже прошедшего IsAdmin-проверку клиента возвращает ошибку из хендлера → клиенту уходит `PROTOCOL_ERROR` (не молчаливый no-op — это должно быть недостижимо при корректном фронте).
- ✅ `Realtime`: `subscribers` → `map[*ws.Client]map[scopeKey]struct{}`, `Subscribe` заменяет scope целиком при повторном вызове, `BroadcastDetail` фильтрует `update.Points` по scope на клиента и не шлёт сообщение вовсе, если после фильтра пусто.
- ✅ Локальный тип `scopeKey`/`ScopeEntry`/`buildScopeSet` в новом файле `internal/metrics/scope.go` (не импортировали из Flatline — раздельные модули, копия архитектуры, не кода).
- ✅ Тесты: `realtime_test.go` (фильтрация рассылки, замена scope при повторной подписке — без merge), `http_test.go`-аналог в `realtime_test.go` (валидация scope, 400 без него/без `metricNames`), `scope_test.go` (юнит-тесты `buildScopeSet`), `flatline_client_test.go` (POST + scope форвардится как есть). `go build`/`go vet`/`go test ./...` — зелёные.
- ✅ После both-review (пересмотрено 08.09.2026): числовой лимит `maxScopeMetrics` убран совсем — ни один вызывающий код на фронте не способен собрать scope из «всего каталога», лимит защищал от несуществующего сценария. Проверки непустого scope/непустого `MetricNames`/непустого `Service` — оставлены. См. [megaapp-front план 32, находка 3](../../megaapp-front/plans/32-metrics-mobile-custom-only-mode.implementation-plan.md).
