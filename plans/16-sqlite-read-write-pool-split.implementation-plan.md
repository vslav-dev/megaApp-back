# Разделение пула соединений SQLite (чтение/запись)

Зависит от: `15-sync-architecture-refactor.implementation-plan.md` (и парного фронтового документа с тем же номером). Делать после него, не раньше.

## Что делаем и зачем

Сейчас всё приложение работает через одно-единственное соединение к БД (`SetMaxOpenConns(1)`). Изначально это ограничение производительности, но по факту оно попутно играет вторую роль — неявный примитив сериализации: транзакция правки веса дневника держит это единственное соединение открытым на всё время своей работы, и именно это (а не какая-то явная блокировка) защищает от гонок при повторных ретраях одного и того же запроса (см. `09-food-diary-history-idempotent-edit.implementation-plan.md`).

Цель этого плана — узко: расширить пул на чтение (несколько параллельных соединений вместо одного), оставив запись сериализованной, и сделать это **не сломав** идемпотентность, которая сейчас случайно держится на этом же ограничении.

## Предыстория

Разговор с пользователем: было ощущение, что подобное уже пробовали включать раньше и почему-то откатили, точная причина не вспомнилась. Проверка git-истории `internal/platform/sqlite/db.go` следов такой попытки не показала — `SetMaxOpenConns(1)` стоит с самого первого коммита файла, без правок. Прошлая попытка (если она была) либо не коммитилась, либо относится к другому месту/проекту. Достоверно неизвестно — не является блокером, просто зафиксировано как открытый вопрос, специально не расследовалось глубже по просьбе пользователя.

Что действительно установлено анализом (не догадка): в текущем коде есть как минимум один явный случай, где чтение и запись держатся в одной открытой транзакции через сервисный слой (правка записи дневника) — наивное расширение пула само по себе эту транзакцию не сломает (она сама управляет своим соединением), но общий пул из нескольких равноправных соединений снимает гарантию «есть только одно соединение — значит все операции сериализованы сами по себе», на которую сейчас неявно опирается идемпотентность. Без явной замены этой гарантии на что-то другое расширение пула — именно тот риск, из-за которого, вероятно, и было решено (сейчас или в прошлый раз) от него отказаться.

## Почему делать только после плана 15

План 15 вводит версию/свежесть на сущности и протокольную идемпотентность вместо неявной защиты через единственное соединение. Как только идемпотентность перестаёт зависеть от размера пула, расширять пул на чтение становится безопасно. Делать это раньше — воспроизвести тот же класс гонки, ради устранения которой всё это затевалось, только в новом месте.

## Направление решения (без глубокой проработки)

- Читающие запросы — через пул с несколькими соединениями.
- Пишущие операции и любая транзакция, держащая соединение открытым между чтением и записью (как в правке дневника) — через выделенное соединение записи, без исключений и неявных попаданий в пул чтения.
- Явно проверить (после плана 15), что идемпотентность операций базируется на версии/проверке в транзакции, а не на побочном эффекте однопоточности пула — это условие готовности к данному плану, а не часть его собственной работы.

## Чеклист

- ✅ Читающий пул (`internal/platform/sqlite/db.go`: `Read()`, 4 соединения) и пишущее соединение (`Write()`, `MaxOpenConns=1`) — два разных `*sql.DB`, один файл, DSN с `_pragma=` (не разовый `ExecContext`) — иначе `foreign_keys`/`synchronous`/`busy_timeout` применились бы только к одному соединению из пула. `money`/`food`/`auth`/`settings`/`quotes` — второе поле `write` в `Repository`, все `Create/Update/Delete` без явной `tx` переведены на него.

## Код-ревью после реализации (2026-07-31, третья сессия)

Отдельный проход код-ревью по итоговому диффу. Ничего критичного не найдено — три находки, все низкого/среднего приоритета, ни одна не блокировала использование. По решению пользователя все три исправлены сразу, включая полноценный вариант первой (именной тип, не просто комментарий).

- ✅ **Нет защиты от случайной записи через read-пул в будущем — исправлено именным типом.** Введён `sqlite.WriteDB` (`internal/platform/sqlite/db.go`) — обёртка над `*sql.DB` (`type WriteDB struct { *sql.DB }`), структурно отличная от голого `*sql.DB` read-пула. `DB.Write()` возвращает `WriteDB`, а не `*sql.DB`. Поле `write` во всех 5 репозиториев (`money`, `food`, `auth`, `settings`, `quotes`), `idempotency.Store` и `backup.Service` теперь имеет тип `sqlite.WriteDB` — перепутать его с read-пулом (`db *sql.DB`) стало ошибкой компиляции, а не тихим рантайм-багом. Методы (`ExecContext`/`QueryRowContext`/`BeginTx`/`PrepareContext`) продолжают работать без изменений благодаря embedding.
- ✅ **`GetQueryEmbedding` — разделено на чтение и best-effort запись.** `GetQueryEmbedding` (`internal/food/search_repo.go`) теперь только `SELECT` через `r.db` (read-пул). Инкремент счётчика обращений вынесен в отдельный метод `RecordQueryEmbeddingHit` через `r.write`, вызывается из `catalogue_service.go` (`searchCatalogueIDsByEmbedding`) после успешного попадания в кэш, ошибка игнорируется (`_ = ...`) — потерять один инкремент счётчика популярности не страшно, а поиск больше не должен падать из-за этого.
- ✅ **Дублирование в `db.go` устранено.** Открытие write- и read-пула вынесено в `openPool(dsn string, maxConns int) (*sql.DB, error)`, вызывается дважды с разным `maxConns`.

Все правки покрыты существующим прогоном тестов (`go build/vet/test ./...` — зелёный), тестовые файлы (5 пакетов + `idempotency`, `backup`, `ws`, `metrics`) обновлены под новый тип `sqlite.WriteDB{DB: db}`.

## Код-ревью диффа (2026-07-31, `/code-review low`)

Автоматический быстрый проход по итоговому диффу (без верификации). Одна находка, по перепроверке — ложная.

- ❌ **Не подтвердилось**: «`Close()` (`db.go`) закрывает read-пул без таймаута перед чекпоинтом — зависшее/занятое read-соединение может повесить весь shutdown навсегда». Перепроверено по исходникам Go (`database/sql/sql.go:926-958`, `func (db *DB) Close()`): `sql.DB.Close()` закрывает только **свободные** соединения из пула (`db.freeConn`), не ждёт занятые — просто помечает пул закрытым (`db.closed = true`) и возвращается. Зависания на «застрявшем» читающем соединении не происходит ни при каких условиях. Правка не потребовалась.
