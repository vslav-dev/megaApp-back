# Дневник еды: черновик правки vs фоновое обновление данных (бэкенд-часть)

Парный документ: `megaapp-front/plans/17-food-diary-draft-vs-background-refresh-race.implementation-plan.md` — там разбор бага и реализация.

## Что делаем и зачем

Основной документ закрывает гонку «фоновый перезапрос данных дневника перезатирает несохранённый ввод в открытой форме правки/добавления записи». По итогам анализа причина и фикс целиком на фронтенде: форма путает «пришли новые базовые данные» с «нужно стереть черновик пользователя». Протокол между фронтом и бэкендом (формат ответов, WS-сообщения, `operationId`/версия записи из плана `15`) уже несёт всё необходимое и не требует изменений для этого фикса.

**Вывод: обязательных изменений на бэкенде в этом раунде нет.**

## Почему бэкенд не тронут

- `SYNC_STATUS` (`internal/ws/hub.go`) как источник триггера для фронта остаётся ровно тем же по контракту — метка времени последнего изменения по пользователю, отдаётся при подключении. Фронт по итогам анализа решил не менять частоту/условия перезапроса по этому триггеру в этом раунде (см. основной документ, «рассмотрено и не берём») — а если бы менял, для этого хватило бы уже отдаваемого значения, без изменения формата.
- Версия записи (`DiaryEntry.version`, план `15`) и защита от гонки «сабмит → подтверждение» (`pendingDiaryEntryIds`, тоже `15`) — не имеют отношения к этому багу, он в окне **до** сабмита, где ни версия, ни `operationId` ещё не участвуют.
- Пограничный случай «правка записи с другого устройства, пока на этом открыта форма с непустым черновиком» (см. основной документ, ждёт решения пользователя) — при любом из предложенных вариантов ответа (молча пересчитать проекцию от нового базового веса / не трогать до явного действия пользователя) решается целиком на фронте существующими данными realtime-события `DIARY_ENTRY_UPDATED` — новый вес и так в нём уже есть. Бэкенд ничего дополнительно передавать не должен.
