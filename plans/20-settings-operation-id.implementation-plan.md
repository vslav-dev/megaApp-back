# Настройки на стандарт operationId

Источник: разбор бага `PUT /api/settings/` 400 (лишний `operationId` в теле ломал строгую проверку `len(payload) != 1` в `ParseUpdateInput`). Временный фикс — `delete(request, "operationId")` в `http.go` — работает, но settings остаётся единственным потребителем `SyncEngineService`, чей бэкенд не подключён к `internal/platform/idempotency` (план `15` прямо оставил этот контракт открытым именно для такого подключения позже, план `18` — свежий прецедент того же самого для каталога еды). Цель этого документа — сделать то же самое для settings, тем же паттерном, без исключений по домену.

## Что делаем и зачем

`operationId` генерируется движком синка на фронте (`sync-engine.service.ts`) и подмешивается в тело **любого** CREATE/UPDATE/DELETE-запроса независимо от домена — фронт не выбирает, включать его или нет. Дневник еды, каталог еды и деньги уже умеют по этому токену отличать повтор запроса (ретрай после таймаута, повтор после перезагрузки страницы через `restorePendingOperation()`) от нового — и на повторе возвращают закэшированный результат вместо повторного применения. Settings — единственный домен на этом движке, где бэкенд токен просто отбрасывает и повторно применяет обновление безусловно.

Практический риск сегодня невысокий (PUT настройки — перезапись одного скалярного поля, естественно «последняя запись побеждает»), но это нарушает предпосылку, на которой построен весь `restorePendingOperation()` (план `16`, фронт: «бэкенд идемпотентен по `operationId` — жёсткая предпосылка»). Раз single-user фаст-режим — не повод тащить в проект несогласованные исключения (см. правило избегания оверинжиниринга); наоборот — несогласованность между доменами сама по себе источник багов вроде того, что уже словили. Приводим к общему стандарту.

## Текущая реализация (обзор)

- `internal/settings/repo.go` — `Repository.Upsert` пишет прямо через `r.write.ExecContext(...)` (`UPDATE`, при нуле задетых строк — fallback на `INSERT`), без параметра транзакции. Ни один метод репозитория не принимает `*sql.Tx`.
- `internal/settings/service.go` — `Service` содержит только `repo`, без `idempotency`. `Put(ctx, userID, input UpdateInput) error` — просто мёржит одно поле в `StoredSettings` и вызывает `Upsert`. Возвращает голый `error`, без `(applied bool, err error)`.
- `internal/settings/http.go` — `Put`-хендлер декодирует тело в `map[string]any`, сейчас просто удаляет ключ `operationId` (последний фикс) и не проверяет его наличие вообще.
- `internal/httpx/modules.go`, `buildSettingsModule` — единственная из трёх (`buildMoneyModule`/`buildFoodModule`/`buildSettingsModule`), которая не создаёт и не передаёт `idempotency.NewStore(write)` в конструктор сервиса.
- Фронт (`settings.service.ts`, `updateSetting`) уже полностью на `SyncEngineService`: `mode: Optimistic`, `type: UPDATE`, `rollbackCallback` — ровно то же самое, что есть у денег и еды. `operationId` в тело подмешивает сам движок, домен-сервис его не видит и не должен — тут ничего не сломано и трогать нечего.

## Какой паттерн подключения повторяем

В кодовой базе два прецедента, выбор между ними определяется наличием кросс-табличных проверок между «проверить» и «записать»:

- **Паттерн A (дневник еды, `food/service.go`)** — одна транзакция на всё: `BeginTx` → `Find` → если найдено, откатить и вернуть закэшированный результат → если нет, тут же в этой же транзакции применить изменение → `Record` → `Commit`. Годится, когда между проверкой и записью не нужно читать что-то ещё через read-пул.
- **Паттерн B (деньги, каталог еды — план `18`)** — `peekIdempotency`: короткая транзакция только на `Find`, сразу закрывается; затем валидация/кросс-табличные проверки через read-пул (иначе дедлок единственного write-соединения); затем вторая, настоящая транзакция на запись + `Record` + `Commit`. Нужен, когда между проверкой и записью обязательны внешние проверки (уникальность имени, существование счёта/категории, генерация эмбеддингов и т.п.).

Settings не имеет кросс-табличных проверок вообще (`Put` просто мёржит одно поле и апсертит ту же строку) — значит **берём паттерн A**, как у дневника, без `peekIdempotency`.

Версия записи (`ver`) — не нужна, по той же логике, что уже применена к дневнику и каталогу (план `15`, `18`): `ver` нужен только там, где есть risk конфликта с realtime-обновлением уже открытой формы поверх устаревших данных. У settings такого сценария нет — это личные тумблеры одного пользователя, никакого параллельного редактирования с двух мест.

Кэшируемый результат — минимальный, без полезной нагрузки (как у `DeleteTransaction`/`DeleteDiaryEntry`): в settings нет server-assigned id, который нужно было бы вернуть и на повторе переиспользовать. Достаточно закэшировать сам факт «применено» без данных.

## Область охвата

Только бэкенд: `internal/settings/repo.go`, `service.go`, `http.go`, `internal/httpx/modules.go`. Миграция не нужна — `syncOperations` уже полностью общая таблица (`id, userId, createdAt, resultJSON`, без привязки к домену), просто начнёт получать строки и от settings.

Фронт не меняется. `settings.service.ts` уже отправляет `operationId` через общий `SyncEngineService` ровно так же, как деньги и еда — асимметрии (нет `successCallback`/pending-id-set, в отличие от денег/еды) не баг, а следствие того, что у settings нет создаваемой сущности с сервер-присвоенным id, который нужно было бы сверять.

Вне охвата, оставляем как есть:
- `POST /api/settings/` (полная перезапись объекта) — не используется движком синка с фронта вообще, `operationId` через него не идёт.
- `/api/metrics-settings/` (GET/PUT) — отдельный поддомен в этом же пакете, на `SyncEngineService` не переведён на фронте, `operationId` не участвует.

## Затронутые флоу

| Флоу | Сейчас | После |
|---|---|---|
| `PUT /api/settings/` без `operationId` | Проходит (поле молча выбрасывается) | 400 «operationId is required» — как у всех остальных доменов |
| `PUT /api/settings/` с валидным `operationId`, успех | Применяется | Не меняется |
| Ретрай того же `operationId` (таймаут, `restorePendingOperation()` после перезагрузки страницы) | Применяется повторно безусловно — не страшно для скаляра, но нарушает предпосылку плана `16` | Возвращает закэшированный результат первой попытки, повторного апсерта нет |
| `PUT /api/settings/` с невалидным именем поля / больше одного ключа | 400 (`ErrInvalidSetting`/`ErrInvalidSettingPayload`) | Не меняется — `operationId` по-прежнему исключается из подсчёта ключей до `ParseUpdateInput`, только теперь через явную переменную, а не удаляется вслепую |

## Реализовано (2026-08-02)

- `internal/settings/repo.go` — `Upsert` и `GetByUserID` переведены на общий интерфейс `txRunner` (`ExecContext`+`QueryRowContext`, реализован и `*sql.DB`, и `*sql.Tx`) — тот же паттерн, что уже применён в `internal/money/repo.go`. Один метод `GetByUserID(ctx, tx txRunner, userID)` обслуживает и обычное чтение (`s.repo.db`), и чтение внутри транзакции — без дублирования SQL между двумя версиями (изначально было две почти идентичных функции, `GetByUserID`/`GetByUserIDTx` — поправлено по итогам code review).
- `internal/settings/service.go` — `Service` получил поле `idempotency *idempotency.Store`, `NewService(repo, idempotencyStore)`. `Put` — паттерн A (как у дневника): `BeginTx` → `Find` → найдено: откат, `(false, nil)` → не найдено: `GetByUserIDTx` → применить поле → `Upsert` тем же `tx` → `Record` (кэш — пустой `"{}"`, отдавать после повтора нечего) → `Commit` → `(true, nil)`. Заодно поправлены два побочных вызова `Upsert`, которые перестали компилироваться после смены его сигнатуры: `Get` (создание дефолтной строки при первом заходе) и `Post` (полная перезапись) — оба оборачивают свою запись в отдельную транзакцию через `s.idempotency.BeginTx` (без `Find`/`Record` — у них нет `operationId`, это не часть протокола идемпотентности).
- `internal/settings/http.go`, `Put`-хендлер — `operationId` теперь читается в переменную и проверяется на пустоту (400 «operationId is required», как у остальных доменов) **до** удаления ключа из map для `ParseUpdateInput`.
- `internal/httpx/modules.go`, `buildSettingsModule` — `settings.NewService(repo, idempotency.NewStore(write))`.
- Тесты: `TestSettingsEndpoints` (`http_test.go`) — существующие PUT-тела получили `operationId`; добавлены проверка повтора того же `operationId` (второй PUT с другим полем и тем же id должен быть проигнорирован — `liteVersion` остаётся `false`) и проверка 400 без `operationId`. `service_test.go` — новый `TestPutSameOperationIDReplaysWithoutReapplying`, все конструкторы сервиса — через общий `newTestService` с `idempotency.NewStore`. Обе тестовые схемы получили таблицу `syncOperations`.
- `go build ./...`, `go vet ./...`, `go test ./...` — все зелёные.
