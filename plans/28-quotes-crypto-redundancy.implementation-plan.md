# QUOTES-CRYPTO-REDUNDANCY: Implementation Plan

## Задача

Вернуть надёжный сбор крипто-котировок: убрать мёртвый источник (CryptoCompare), восстановить реальную
избыточность (≥2 источника на каждый тикер), закрыть слепую зону логирования, забэкфилить пропущенные даты.

## Диагностика (проведена, факты подтверждены)

**Регрессия, а не новая проблема.** Исходный дизайн (`plans/MONEY-QUOTES._design-doc.md`) требовал
маппинг CoinGecko на ВСЕ 8 крипто-тикеров (BTC, ETH, XRP, XMR, DASH, ZEC, GLM, ARK) как ПЕРВИЧНЫЙ источник.
В текущей Go-реализации (`internal/quotes/fetcher.go`) в маппинге на CoinGecko остались только BTC и ETH —
остальные 6 тикеров эту стадию всегда пропускают. Похоже, маппинг потерялся при переписывании бэкенда с
Node.js на Go. Из-за этого реальная избыточность для 6 из 8 монет всегда была ниже задуманной: CoinGecko
(primary) → CryptoCompare (fallback) → Yahoo → Binance превратилось в no-op → CryptoCompare → Yahoo → Binance.

**Триггер обвала — 2026-03-29.** До этой даты (проверено по `moneyRateHistory` с 2015 года) крипто-котировки
собирались стабильно ~100% дней. Начиная с 2026-03-29 — систематические пропуски (апрель–август 2026: от
30% до 70% дней без единой крипто-котировки). Код в этот период не менялся (`git log` по `internal/quotes`
пуст в этом окне) — причина внешняя: CryptoCompare (`min-api.cryptocompare.com`) сейчас отвечает `401
API key required` на любой запрос — провайдер закрыл бесплатный доступ. Совпадение по времени с началом
обвала — веский довод, что это и есть спусковой крючок: как только сломался единственный реальный fallback
для 6 из 8 монет (CoinGecko для них не работал изначально из-за регрессии), у этих монет не осталось
рабочего источника в дни, когда Yahoo/Binance тоже давали сбой.

**Проверена индивидуальная доступность источников (live-запросы с сервера, только на чтение):**

| Тикер | CoinGecko (после фикса маппинга) | Yahoo | Binance |
|-------|-----------------------------------|-------|---------|
| BTC, ETH, DASH, ZEC, ARK, GLM, XRP | ✅ | ✅ | ✅ |
| XMR | ✅ | ✅ | ❌ (пара делистнута с Binance) |

CryptoCompare — ❌ для всех тикеров (требует платный API-ключ, в коде ключ нигде не передаётся).

**Вывод по избыточности:** после удаления CryptoCompare и восстановления CoinGecko-маппинга на все 8
тикеров получаем 3 независимых источника для 7 монет и 2 для XMR — этого достаточно, отдельный третий
провайдер не нужен.

**Почему одновременно молчали и остальные источники — до конца не выяснено.** Прямых логов по каждому
источнику нет (см. слепую зону ниже), поэтому нельзя точно сказать, был ли это рейт-лимит от бесплатных
тарифов CoinGecko/Yahoo/Binance именно в момент запуска джобы (03:00 UTC), или самоиндуцированный throttling
из-за того, что код бьёт по всем тикерам подряд без пауз (до ~30 запросов в несколько секунд на один и тот
же хост). Быстрое время выполнения джобы в дни сбоя (~4 сек на весь прогон) говорит за быстрые отказы
(429/rate-limit), а не за сетевые таймауты. Это гипотеза, которую должно подтвердить или опровергнуть
логирование после фикса — окончательный вывод будет виден по логам первых недель работы.

**Слепая зона логирования.** `internal/httpx/modules.go` вызывает `service.Run(ctx)` и отбрасывает
результат (`RunResult.Errors` — список тикеров, по которым не вышло скачать ничего). В лог пишется только
факт завершения джобы с длительностью — ни один частичный сбой за 5 месяцев не был виден.

**Отдельно замечено, вне скоупа этой задачи:** примерно в те же даты (~9-10 марта 2026) перестали
приходить котировки части российских акций через MOEX (число тикеров в `ratesJson` заметно упало).
Не расследовалось — возможно, отдельная проблема с MOEX-источником, требует отдельного разбора при
необходимости.

## Архитектура решения

1. **Источники крипто-котировок:** CoinGecko (маппинг на все 8 тикеров) → Yahoo → Binance, в этом порядке.
   CryptoCompare убрать полностью (конфиг символов, вызов, обработку ответа).
2. **Наблюдаемость:** джоба должна логировать результат каждого запуска — сколько тикеров успешно
   обновлено, какие тикеры остались без цены и на каком источнике каждый из них споткнулся (а не только
   факт "не вышло совсем"). Это нужно и для диагностики текущей причины, и на будущее.
3. **Пауза между запросами — НЕ ДЕЛАТЬ СЕЙЧАС, только по факту из логов.** Это неподтверждённая гипотеза
   (ничем не доказана, кроме косвенного "джоба в дни сбоя отрабатывала подозрительно быстро"). Задержка
   между последовательными запросами к одному провайдеру снизила бы риск самоиндуцированного рейт-лимита
   — ЕСЛИ рейт-лимит вообще является причиной. Внедрять только после того, как логирование (п.2) явно
   покажет 429/рейт-лимит как реальную причину сбоев в проде. Без такого подтверждения — не трогать.
4. **Бэкфилл:** после фикса — разовый прогон джобы (или временное увеличение `QUOTES_FETCH_DAYS`) с
   диапазоном дат 2026-03-29 → сегодня, чтобы дозаполнить все "дырявые" записи в `moneyRateHistory`.
   Существующий merge-механизм (сохраняет уже известные тикеры, дополняет недостающие) это позволяет
   без риска затереть то немногое, что уже успешно сохранилось за эти дни.

## Блок 2: полная трассировка ценового флоу (2026-08-25)

Найдено после деплоя фикса из Блока 1: график Account Balances не сдвинулся (676k → 680k → 690k при
многократных рефрешах), несмотря на то что бэкенд после фикса реально дособрал все 8 крипто-тикеров за
24 августа. Расследование ниже прослеживает цену от внешнего API до пикселя на графике, шаг за шагом, без
пропусков — потому что предыдущий раунд анализа упустил критичный слой (backend-фильтрация снапшота +
frontend-протяжка), из-за чего диагноз "готово, обновись" оказался неверным.

### Шаг 1 — фетч у провайдера (`internal/quotes/fetcher.go`)

Для крипто-тикера пробуются по порядку, с переходом на следующий при неудаче (`cryptoSources`,
[fetcher.go:234](internal/quotes/fetcher.go#L234)):

1. **CoinGecko** — `GET /api/v3/coins/{id}/market_chart/range?vs_currency=usd&from=...&to=...`. Тикер → id
   через статическую карту `coinGeckoIDByTicker` ([fetcher.go:54](internal/quotes/fetcher.go#L54)): BTC→bitcoin,
   ETH→ethereum, XRP→ripple, XMR→monero, DASH→dash, ZEC→zcash, GLM→golem, ARK→ark. Ответ — массив
   `[unixMs, price]`, конвертируется в дату по UTC (`time.UnixMilli(...).UTC().Format("2006-01-02")`).
   Бесплатный тариф — жёсткий рейт-лимит, часто отвечает `429` при батче из 8+ тикеров подряд без пауз.
2. **Yahoo Finance** — `GET /v8/finance/chart/{TICKER}-USD?period1=...&period2=...&interval=1d`. Ответ —
   параллельные массивы `timestamp[]` и `indicators.quote[0].close[]`; дата = `time.Unix(ts,0).UTC()`. Если
   `close[i] == nil` — эта дата **молча пропускается** ([fetcher.go:315](internal/quotes/fetcher.go#L315)), не
   считается ошибкой, остальные даты диапазона возвращаются нормально.
3. **Binance** — `GET /api/v3/klines?symbol={TICKER}USDT&interval=1d&startTime=...&endTime=...`. Close —
   элемент `[4]` каждой свечи. Для XMR пары `XMRUSDT` не существует (делистнута) — источник всегда пуст.

Валюты (`currencySources`, [fetcher.go:205](internal/quotes/fetcher.go#L205)): Yahoo (`EURUSD=X`,
`USDRUB=X` с инверсией для RUB/KZT) → Frankfurter (только EUR/GBP) → exchangeRate.host (universal
fallback). Акции/облигации — только MOEX (`stockSources`/`bondSources`), без фоллбека вообще: если MOEX не
отдал данные (`moex: empty response`) — тикер полностью без цены за этот прогон (см. сегодняшний лог: FXCN,
FXRU, FXUS, RUSB, KZT).

**Найденный в этом расследовании баг Yahoo:** дневная свеча за только что закрывшийся UTC-день у Yahoo
иногда ещё не опубликована (проверено живым запросом — свеча за 24.08 в 02:40 UTC отсутствовала/была
`null`, к 09:00 UTC того же дня уже была доступна с реальным значением). Источник в этом случае возвращает
непустую карту (другие даты диапазона есть), поэтому логируется как `"yahoo: ok"` (успех) — но **конкретно
самая свежая дата остаётся без цены**, и это не отражается ни в `Failures`, ни в `Degraded`, потому что
формально тикер получил цену (просто не за нужный день).

### Шаг 2 — ретраи и классификация исхода (`fetchTickerWithFallbacks`, [fetcher.go:167](internal/quotes/fetcher.go#L167))

На каждый источник — до `QUOTES_RETRY_ATTEMPTS` (3) попыток с паузой `QUOTES_RETRY_DELAY_SECONDS` (30с)
между ними, но **только** для транзиентных ошибок (5xx или сетевая ошибка); `429` и прочие 4xx —
немедленный переход к следующему источнику без ретрая. Результат тикера классифицируется
(`recordTickerOutcome`, [fetcher.go:149](internal/quotes/fetcher.go#L149)):
- первый источник сразу успешен → ничего не логируется (здоровый путь, шум не нужен);
- сработал не первый источник → `Degraded` (кто-то деградирует, но данные есть);
- ни один источник не дал данных → `Failures`.

### Шаг 3 — что реально пишется в БД (`service.go` `Run()`, [service.go:38](internal/quotes/service.go#L38))

1. `ListRateHistoryRange(fromISO, toISO)` — читает **уже существующие** строки за окно дат в `ratesMap`.
2. Для каждого класса тикеров (currency/crypto/stock/bond) фетчится диапазон и **сливается поверх**
   (`mergeRatesMap`, [service.go:150](internal/quotes/service.go#L150)): `if value != 0 { target[date][ticker] =
   value }` — **безусловная перезапись** уже существующего значения новым, если новое ненулевое. Значит
   повторный ручной/автоматический прогон джобы может слегка изменить уже сохранённую историческую цену
   (если апстрим отдаёт чуть другое число при повторном запросе того же дня — актуально для самых свежих
   дат диапазона, где "исторический" close у провайдера ещё не полностью устоялся).
3. `UpsertRateHistoryEntry` ([quotes/repo.go:47](internal/quotes/repo.go#L47)) — `INSERT ... ON CONFLICT(dateISO)
   DO UPDATE SET ratesJson = excluded.ratesJson`, **весь JSON дня целиком перезаписывается** объединённой
   картой (старые тикеры, которых не было в новой выборке, сохраняются, т.к. `ratesMap` строился поверх уже
   прочитанных данных на шаге 1).

**Окно джобы принципиально не включает "сегодня":** `toDate = now - 1 день`
([service.go:134](internal/quotes/service.go#L134)) — сегодняшняя дата никогда не фетчится тем же днём, только
на следующий день, когда она уже становится "вчера".

**Самоисцеление:** `QUOTES_FETCH_DAYS=7` — каждый прогон пере-фетчит скользящее окно в 7 дней, поэтому
пропуск (как у Yahoo-задержки выше) закрывается сам на следующий день без вмешательства — если только цена
за эту дату не понадобилась фронту раньше, чем джоба до неё доберётся повторно.

**Расписание:** `QUOTES_JOB_SCHEDULE=40 2 * * *` (крон, UTC) — раз в сутки в 02:40 UTC. Подтверждено логом:
единственный автозапуск сегодня в `2026-08-25T02:40:07Z`.

### Шаг 4 — ручной запуск в обход крона (`/api/debug/run-quotes-job`, [quotes/http.go](internal/quotes/http.go))

Роут зарегистрирован напрямую на роутере ([httpx/app.go:143](internal/httpx/app.go#L143)) **без auth-мидлвари**
(в отличие от `money.RegisterRoutes`, куда явно передаётся `authModule.service`) — не защищён токеном/сессией
в принципе. Смягчающий фактор: сервис слушает только `127.0.0.1:3000`
(подтверждено `ss -tlnp` на сервере), т.е. недоступен напрямую снаружи, только с самого хоста или через
реверс-прокси, если тот его отдельно форвардит наружу — это не проверялось в рамках расследования.

Второе: этот путь вызывает `service.Run(ctx)` напрямую и возвращает `Failures`/`Degraded` в JSON-ответе
HTTP-запроса — но **не пишет в journald** ничего (ни `"quotes ticker fetch..."`, ни `"quotes job summary"`).
Эти логи существуют только в крон-обёртке ([httpx/modules.go](internal/httpx/modules.go)). Итог: ручные
прогоны (как несколько сделанных сегодня в рамках этого расследования) не оставляют следа в логах сервера
вообще — видны только в момент самого HTTP-ответа. Отдельный, ранее не описанный слепой участок
наблюдаемости.

### Шаг 5 — чтение снапшота бэкендом (`GetSnapshot`, [money/service.go:39](internal/money/service.go#L39))

Один вызов читает из SQLite: `currencies`, `categories`, `organizations`, `accounts`, `assets`,
`transactions`, **весь** `moneyRateHistory` без пагинации и без фильтра по дате (`ListRateHistory`,
[money/repo.go:742](internal/money/repo.go#L742): `SELECT id, dateISO, ratesJson FROM moneyRateHistory ORDER BY
dateISO ASC` — вся история с 2015 года каждый раз), плюс `investAssetTrades`. Это объясняет замеченные ранее
`4-5 секунд` длительности `GET /api/money/snapshot` в логах — не живой внешний запрос (внешних вызовов в
этом хендлере нет вообще), а просто полное чтение и JSON-парсинг многолетней таблицы при каждом заходе на
страницу.

### Шаг 6 — фильтрация крипто-тикеров: ключевой баг (`filterSnapshotRateHistory`, [money/service.go:772](internal/money/service.go#L772))

```
allowedTickers := currencyTickers  // всегда: EUR, KZT, RUB, USD (проверено live-запросом к moneyCurrency)
if day == daysInMonth(year, month) {   // ТОЛЬКО последний календарный день месяца
    allowedTickers += eomHeld[month]   // крипто/акции, которые держались на конец этого месяца
}
```

`currencyTickers` строится из таблицы `moneyCurrency` — крипта там никогда не значится (только фиатные
EUR/KZT/RUB/USD, подтверждено `SELECT ticker FROM moneyCurrency` на проде). Значит **крипто-тикеры
попадают в отдаваемый фронту `ratesJson` только для одной даты в месяц — последнего календарного дня**.
Для августа это `2026-08-31` — дата, которой физически ещё не существует (сегодня 25-е). Все дни с 1 по 30
августа отдают фронту `ratesJson`, в котором крипты просто нет — даже если в самой БД (`moneyRateHistory`)
цена реально есть (как сейчас, после фикса Блока 1, у 24 и 25 августа).

`eomHeld` (`computeEOMHeldTickers`, [money/service.go:811](internal/money/service.go#L811)) — по каждому
месяцу считает, какие тикеры держались кумулятивно на теоретическую дату конца месяца, суммируя
`invest_buy`/`invest_sell` сделки по дате ≤ конец месяца.

`GetRateHistory` / `/api/money/rate-history` ([money/http.go:529](internal/money/http.go#L529)) — существует
отдельный **нефильтрованный** эндпойнт (просто `ListRateHistory` без прогона через
`filterSnapshotRateHistory`), но фронт его нигде не вызывает (проверено grep по всему `src/` — только
`money.service.ts` знает про rate history, и он ходит исключительно на `/api/money/snapshot`). Мёртвый с
точки зрения текущего UI путь.

### Шаг 7 — кэш и накопление на фронте (`money.service.ts`)

- **localStorage-кэш** `SNAPSHOT_KEY = 'money_snapshot'` ([money.service.ts:75](../../megaapp-front/src/app/services/money.service.ts#L75)):
  при инициализации сервиса сперва синхронно применяется закэшированный снапшот (`applySnapshot(cached,
  true)`), и только после этого асинхронно уходит `fetchSnapshot()` → `GET /api/money/snapshot` →
  `applySnapshot(data, true)` → `writeCacheSnapshot()` (перезаписывает кэш свежими данными). **Это не
  HTTP-кэш браузера** — `Cmd+Shift+R` его не трогает. Каждый заход на страницу на долю секунды показывает
  предыдущее закэшированное состояние, потом перерисовывает актуальным — при быстрых повторных рефрешах
  можно поймать разные промежуточные кадры этой гонки.
- **`rateSnapshots$$`** ([money.service.ts:123](../../megaapp-front/src/app/services/money.service.ts#L123)) —
  computed-сигнал, кумулятивно "протягивает" курсы вперёд по всей истории:
  ```
  accumulated = {}
  for each record in rateHistory (по возрастанию даты):
      accumulated = { ...accumulated, ...record.ratesJson }   // тикеры не сбрасываются, только дополняются/перезаписываются
      snapshot[record.dateISO] = accumulated (копия на этот момент)
  ```
  Раз бэкенд (Шаг 6) отдаёт крипто-тикеры только на датах конца месяца — курс BTC/XRP/... на любую
  "промежуточную" дату месяца в этой структуре фактически равен курсу **последней даты конца месяца, где
  этот тикер вообще был передан**. Обновление джобой ежедневных цен (Шаги 1-3) на эту протяжку не влияет
  никак, пока не наступит следующий конец месяца.
- **`getRatesForDate(dateISO)`** ([money.service.ts:~1097](../../megaapp-front/src/app/services/money.service.ts#L1097)) —
  бинарный поиск по `rateSnapshots$$` на "последняя дата ≤ target", возвращает объект `.rates` целиком (уже
  протянутый).

### Шаг 8 — построение точки графика (`money-compute.service.ts`)

`buildBalanceChartData()` ([money-compute.service.ts:180](../../megaapp-front/src/app/services/money-compute.service.ts#L180))
для каждого месяца в диапазоне графика вычисляет `eomISO` — **теоретическую** дату конца месяца
(`new Date(yr, mo, 0).getDate()`), не "сегодня", даже для текущего незакрытого месяца — и запрашивает
`getRatesForDate(eomISO)` ([money-compute.service.ts:254](../../megaapp-front/src/app/services/money-compute.service.ts#L254)).
Для августа это `getRatesForDate("2026-08-31")` → бинарный поиск падает на последнюю реально существующую
дату ≤ 31.08 (24 или 25 августа) → но крипто-курсов там нет (Шаг 6) → протянутое значение = последний конец
месяца, где крипта была — **31 июля**.

`sumBrokerPositions()` ([money-compute.service.ts:327](../../megaapp-front/src/app/services/money-compute.service.ts#L327))
берёт `rates[ticker]` из этого объекта; если тикера нет или курс `<= 0` — молча пропускает позицию
(**не ошибка, не 0 явно показанный — просто не участвует в сумме**), это тот самый ранее выявленный,
осознанно не включённый в эту задачу frontend-механизм тихого исключения позиции.

### Итоговая цепочка провала для августа — с цифрами

```
moneyRateHistory (БД, после фикса Блока 1):
  2026-07-31: BTC=62 904.77   ← последняя дата, которую видит фронт для крипты
  2026-08-24: BTC=78 649.61   ← реальная, актуальная, лежит в БД, но ОТФИЛЬТРОВАНА на Шаге 6
  2026-08-25: (крипты нет вообще, джоба ещё не фетчила "сегодня")
```

График "Account Balances → август 2026" считает крипто-часть по курсу **31 июля**, заниженному относительно
текущего примерно на 25% по BTC (и аналогично по остальным 7 тикерам). Фикс Блока 1 (источники, редандантность,
логирование) целиком корректен и подтверждён логами/БД, но **структурно не мог повлиять на отображаемое
число** — данные, которые он чинит, до фронта не доходят вплоть до 31 августа этого месяца, когда впервые
появится настоящая EOM-запись с уже исправленными источниками.

### Сопутствующие находки (не блокируют это расследование, но затрагивают те же цены)

- `KZT` (exchangeRateHost) и `FXCN`/`FXRU`/`FXUS`/`RUSB` (MOEX) стабильно проваливаются в логах — отдельная,
  не расследованная в этой задаче проблема источников для этих конкретных тикеров.
- Акции/облигации не имеют фоллбека вообще — только MOEX, без резервного источника.
- `/api/debug/run-quotes-job` не защищён auth и не логируется в journald — наблюдаемость ручных прогонов
  ограничена только HTTP-ответом в момент вызова.
