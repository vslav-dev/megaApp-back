# Унификация хранения настроек — Implementation Plan (Backend)

Парный план: `megaapp-front/plans/27-settings-persistence-unification.implementation-plan.md`.

## Суть

Заменить нынешний гибрид (жёсткие колонки под core-настройки + один JSON-блоб под metrics, обе в таблице `settings`) на единый generic-механизм: одна таблица вида "пользователь × namespace × JSON-payload", один repo/service/http слой в `internal/settings` на все домены. Новая настройка внутри существующего домена — просто новое поле в Go-структуре, без миграции. Новый домен — одна строка при первом сохранении, без `ALTER TABLE`.

## Текущее состояние

- Таблица `settings` (`000001_auth_and_settings.sql`): одна строка на пользователя, колонки `darkTheme`, `selectedChapterFood`, `selectedChapterMoney`, `liteVersion`, `height` + мёртвые `sex`, `birthDate`, `activityLevel`, `goal` (нигде не используются, `grep` подтвердил).
- Та же таблица, колонка `metricsSettings TEXT` (`000006_metrics_settings_column.sql`) — один JSON-блоб под настройки metrics, без какой-либо валидации формы при записи (`UpsertMetricsSettings` пишет что угодно как есть).
- `internal/settings/repo.go`, `service.go`, `http.go` — два параллельных пути в одном пакете: типизированный (`StoredSettings`, `Upsert`, `ParseUpdateInput` со свитчем по известным полям) и слепой JSON passthrough (`GetMetricsSettingsByUserID`/`UpsertMetricsSettings`).
- `PUT /api/settings/` уже полностью на идемпотентности (план `20`): `operationId` обязателен, паттерн A (`BeginTx → Find → merge одного поля → Upsert → Record → Commit`, всё в `internal/platform/idempotency`), ретрай/повтор не даёт двойного применения. Ограничение — ровно одно поле за вызов (`len(payload) != 1` в `ParseUpdateInput`).
- `PUT /api/metrics-settings/` идемпотентности не имеет вообще, фронт (план `11`) сам ушёл от debounce-автосейва к explicit-save именно из-за гонки полной перезаписи блоба между вкладками/устройствами.
- `POST /api/settings/` (полная перезапись объекта) — с фронта не вызывается нигде, мёртвый код.
- `userName`/`isUserAdmin` в ответе `GET /api/settings/` — не настройки, а профиль пользователя (`GetUserAdminAndName` читает таблицу `users`), в новую схему не входят, остаются как есть.

## Целевая схема

Одна таблица `userSettings(usersId, namespace, payload TEXT, updatedAt)`, первичный ключ `(usersId, namespace)`. Namespace — фиксированный allow-list на бэке (не произвольная строка от клиента): `core`, `food`, `money`, `metrics`. Список настроек по namespace — см. фронтовый план (там же и решение "локально vs на сервер" по каждой). Бэку из этого важно только то, что синкается:

- **core**: `selectedChapterFood`, `selectedChapterMoney`. (`darkTheme` реклассифицирован на локальную настройку фронта 09.08.2026 — убран из `CoreSettings` целиком, без миграции, pre-release. `liteVersion` удалён полностью тем же днём — был мёртвым полем без единого читателя ни на фронте, ни на бэке.)
- **food**: `height` (переезжает из core), `statsDateRange`, `statsTopProductsMetric`, `statsAccordionOpenBlocks` (реклассифицированы с локальных на сервер 09.08.2026).
- **money**: `displayCurrency`, `chartRangeStart`, `chartRangeEnd`, `expenseChartYMax`, `convertToUnifiedCurrency` (переименовано из `keepTransactionCurrency` 09.08.2026, полярность инвертирована — дефолт `false`), `enabledCategoryIds`, `yearlyMode`, `showByAccount`, `suspensionFilter`, `enabledAccountIds`.
- **metrics**: без изменений по составу полей, только транспорт/хранение переезжает на общий механизм.

Мёртвые колонки (`sex`, `birthDate`, `activityLevel`, `goal`) и мёртвый `POST /api/settings/` — удаляются, не переносятся никуда.

### `userName`/`isUserAdmin` — намеренно вне `userSettings.payload`

Обсуждали, не завести ли их в namespace `core` "заодно" — решение: нет, не в payload. Разница принципиальная:

- `userName` — identity-данные (`users.username`), сейчас нигде не мутируется после регистрации (`grep` подтвердил — нет ни одного write-пути, кроме `auth.Register`). Не настройка по своей природе, а профиль.
- `isUserAdmin` — авторизационный флаг (`users.isAdmin`), тоже не мутируется нигде, кроме как напрямую в БД. Это граница безопасности: если бы это поле лежало в `userSettings.payload` под namespace `core`, то общий merge-PUT механизм (принимающий с фронта произвольный набор полей текущего namespace) сделал бы его технически перезаписываемым тем же PUT-запросом, что двигает `darkTheme` — то есть открыл бы self-escalation в админа одним PUT-запросом с полем `isUserAdmin: true`. Это ровно тот случай, ради которого ниже вводится строгий whitelist полей вместо "неизвестное — просто сохраняем".

Оба поля остаются как сейчас: читаются `GetUserAdminAndName` из таблицы `users`, домешиваются в ответ `GET /api/settings/core` на уровне сервиса как read-only довесок поверх namespace-payload, никогда не входят в структуру `CoreSettings` и не могут быть переданы через PUT.

## Repo/Service/HTTP — общий механизм

- **Repo**: два generic метода вместо набора точечных — `Get(ctx, userID, namespace) (payload string, err error)` и `MergeFields(ctx, tx, userID, namespace, fields map[string]json.RawMessage) (merged string, err error)`. `MergeFields` читает текущий payload (или `{}`, если строки ещё нет), домешивает переданные top-level ключи, апсертит строку целиком. Один и тот же метод обслуживает и одиночное поле (auto-save: core, food.height, money-тумблеры), и пачку полей разом (explicit-save: metrics жмёт "Сохранить" — в запросе сразу все изменённые ключи). Никакого отдельного "replace всего namespace" пути не нужно — merge с N≥1 ключами и есть replace, когда N покрывает все поля namespace целиком.
- **Service**: у каждого namespace — своя Go-структура с `json`-тегами (`CoreSettings`, `FoodSettings`, `MoneySettings`, `MetricsSettings`) и функция дефолтов. При PUT: смёржить поля → сериализовать → **round-trip валидация**: анмаршалить получившийся payload в структуру namespace; не влезло по типу — 400, ничего не пишем. Это закрывает дыру, которой сейчас нет ни у metrics (вообще без валидации), ни у core (валидация есть, но раскидана по свитчу вручную на каждое поле). При GET: смёржить сохранённый payload поверх дефолтов namespace (новый пользователь / новое поле, ещё не сохранённое раньше, — получает дефолт, а не `null`/пусто). Ключи, которых нет в структуре namespace, — **отклоняются на PUT** (400), а не сохраняются молча "на будущее": строгий whitelist по полям структуры, не lenient passthrough. Это не только проще, но и закрывает саму возможность протащить в payload что-то за пределами объявленных полей (см. разбор `isUserAdmin` выше) — без этого правила пришлось бы держать в уме отдельно, что вот это конкретное поле нельзя пускать, вместо структурного запрета "нельзя ничего, кроме объявленного".
- **Идемпотентность**: без изменений по механике — тот же `internal/platform/idempotency`, тот же паттерн A, что уже вкатан планом `20`. Отличие только в форме входа: `ParseUpdateInput` обобщается с "ровно одно известное поле" на "один или больше полей текущего namespace", без per-field свитча — валидность полей проверяется round-trip через структуру namespace, а не вручную по имени.
- **HTTP**: один маршрут `GET/PUT /api/settings/{namespace}` вместо `/api/settings/` + `/api/metrics-settings/`. `{namespace}` сверяется с allow-list, неизвестное значение — 404. `PUT` без `operationId` — 400, как сейчас у core.

## Broadcast между устройствами (WS)

Цель: изменил настройку на одном устройстве — на другом открытом устройстве/вкладке она применяется сама, без перезагрузки. Не изобретаем новый механизм — переиспользуем существующий generic `ws.Hub` (`internal/ws/hub.go`), ровно тот же паттерн, что уже работает у food diary и metrics (у money, вопреки первому впечатлению из разговора, broadcast сейчас нет вообще — не с чего было копировать, settings в этом смысле такой же чистый домен, как money).

- `buildSettingsModule` (`internal/httpx/modules.go`) получает параметр `hub *ws.Hub` — сейчас его нет вообще, добавляется с нуля.
- Новый `settings.WSRealtimePublisher` (по образу `food.WSRealtimePublisher`, `internal/food/realtime.go`) с одним методом, например `PublishChanged(userID int64, namespace string, fields map[string]json.RawMessage, excludeClientID string)`, вызывает `hub.BroadcastToUser(userID, payload, excludeClientID)` с тем же конвертом `{type: "SETTINGS_UPDATED", payload: {namespace, fields}}`, что уже используют food/metrics.
- Вызывается из PUT-хендлера после успешного коммита, `excludeClientID` — тем же способом, что уже есть у food (`extractClientID(r)`, читает заголовок `X-Client-ID`, который фронт и так шлёт на каждый запрос глобально через интерсептор — с фронта ничего дополнительно прокидывать не нужно).
- **Важно — не копировать существующий баг, а сразу сделать правильно**: план `XX-ws-broadcast-and-token-refresh-fix` уже документирует, что у food/metrics broadcast сейчас синхронный и блокирует HTTP-ответ. Settings — новый код с нуля, поэтому вызов `PublishChanged` сразу делаем асинхронным (в горутине, после `legacy.WriteJSON(...)`), а не по образцу текущего блокирующего вызова у food.
- Дедупликация собственного эха — уже готовый механизм хаба (исключение по `clientId`), ничего сверх этого не нужно.

## Миграция данных

Одна новая миграция (следующий номер после `000008`): создать `userSettings`, перелить существующие строки `settings` — 4 core-колонки в одну JSON-строку namespace `core`, `height` в строку namespace `food`, `metricsSettings` как есть в строку namespace `metrics` (валидна по построению, раз уже лежала в базе) — затем убрать старые колонки/таблицу. Это живые пользовательские данные (не черновая до-релизная миграция), поэтому backfill обязателен в той же миграции, без ручных шагов после деплоя.

## Находки по ревью (codex-review, 09.08.2026)

2. Некорректные старые данные metrics могут уронить сохранение настроек
   - **Важность:** стоит поправить, но маловероятно на практике — единственный писатель этого поля (текущий фронт) всегда шлёт нормальный объект, так что бага сработает только если в базе реально завалялась аномалия с давних времён.
   - **Как сейчас работает:** миграция переносит колонку `metricsSettings` в `userSettings` через `COALESCE(NULLIF(metricsSettings, ''), '{}')` — то есть NULL/пустую строку заменяет на `{}`, а всё остальное копирует как есть.
   - **Что не так:** старый эндпоинт `/api/metrics-settings/` никогда ничего не валидировал, так что теоретически там могло лежать не `{}`-подобное значение, а, например, литерал `null`. Проверено по коду: если payload — ровно строка `"null"`, `MergeFields` распарсит её в `nil`-мапу без ошибки, а следующая строка попытается записать туда поле → паника (перехватывается общим `Recoverer`, но конкретный запрос пользователя падает с 500).
   - **Как поправить:** в миграции подставлять `{}` не только для пустых/NULL значений, но и для всего, что не является JSON-объектом (проверка через `json_valid`/`json_type`).
   - **Как будет работать после правки:** любые уже сохранённые «мусорные» значения metrics превращаются в пустой объект при переносе, PUT/GET после миграции не падают ни при каких исторических данных.
   - **Статус:** осознанно отклонено. Миграция уже прогнана на текущей проде базе — ни ошибок, ни паники, разовый перенос уже состоялся успешно. Риск не актуален для существующих данных; принят как несерьёзный.

5. Порядок broadcast-ов не гарантирован при быстрых подряд PUT
   - **Важность:** мелочь, но стоит поправить. Нужны именно два быстрых подряд PUT от одного пользователя — на практике очень редко, и тоже само лечится следующим `GET`.
   - **Как сейчас работает:** после каждого PUT рассылка в WebSocket идёт в отдельной горутине (`go h.realtime.PublishChanged(...)`), не дожидаясь остальных.
   - **Что не так:** если один и тот же юзер быстро отправит два PUT подряд (например, быстро дважды переключить чекбокс), эти две горутины ничем не синхронизированы — вторая может физически уйти в сокет раньше первой. Другая вкладка получит апдейты в неправильном порядке и после этого будет показывать более старое значение, хотя в БД уже актуальное.
   - **Как поправить:** рассылать последовательно на пользователя (например, через очередь на hub) или добавить версию/timestamp в сообщение, чтобы клиент отбрасывал более старые.
   - **Как будет работать после правки:** другие вкладки всегда видят события в том порядке, в котором они реально закоммитились.
   - **Статус:** ✅ исправлено. `Repository.upsert` возвращает millisecond-timestamp записи (`repo.go`), прокинут через `Service.Put` → `WSRealtimePublisher.PublishChanged` → payload `SETTINGS_UPDATED.updatedAt`. Фронт (`NamespaceSettingsStore.handleIncoming`) отбрасывает broadcast, если его `updatedAt` не новее уже применённого. Тесты обновлены (`service_test.go`, `http_test.go`), `go build`/`go vet`/`go test ./...` зелёные.

## Находки после ревью (codex-review, 09.08.2026, второй проход)

11. Целевая норма белка теперь всегда считается по `goal = "lose"`

12. `Get()` для `metrics` молча теряет поля, которых нет в текущей Go-структуре

Старый эндпоинт `/api/metrics-settings/` никогда не валидировал форму данных — в накопленном годами блобе теоретически могут быть поля, которых в сегодняшней структуре нет.

13. Версия WS-broadcast (`updatedAt`, миллисекунды) не строго монотонна
    - **Важность:** мелочь, но стоит поправить.
    - **Как сейчас работает:** `Repository.upsert` использует `time.Now().UnixMilli()` как версию записи для сортировки broadcast-сообщений на фронте (`NamespaceSettingsStore` отбрасывает всё не новее уже применённого).
    - **Что не так:** два PUT одного пользователя, попавшие в одну и ту же миллисекунду по настенным часам, получат одинаковый `updatedAt` — клиент не сможет строго отличить, какое из двух сообщений реально новее, если они придут не в порядке отправки.
    - **Как поправить:** заменить wall-clock миллисекунды на строго монотонный источник (счётчик/`UnixNano`/монотонная последовательность в БД).
    - **Как будет работать после правки:** порядок применения broadcast гарантирован даже при коллизии по времени.
    - **Статус:** 🚫 по решению пользователя игнорируем.

14. PUT молча принимает `null` для обязательных bool-полей
    - **Важность:** стоит поправить.
    - **Как сейчас работает:** `validateWhitelist`/`validateRoundTrip` разбирают входящий JSON через `json.Unmarshal` в типизированную структуру namespace.
    - **Что не так:** `encoding/json` в Go молча игнорирует `null` при анмаршалинге в не-pointer поле (например `bool`) — не ошибка, просто "оставить как есть". Значит `PUT {"selectedChapterFood": null}` проходит обе проверки без ошибки, а в БД реально сохраняется `"selectedChapterFood": null` вместо булева значения — регрессия по сравнению со старым ручным свитч-валидатором, который принимал только настоящий bool.
    - **Как поправить:** отдельно отклонять `null` для полей, которые в Go-структуре не указатели (разрешать `null` только там, где поле объявлено как `*T`, например `height`).
    - **Как будет работать после правки:** `null` для обязательного поля — явная ошибка 400, а не тихая порча данных.
    - **Статус:** ✅ исправлено. Новая `rejectNullForNonPointerFields()` в `service.go`: через reflection строит по json-тегам структуры namespace карту "поле → указатель ли", вызывается из `validateWhitelist()` перед декодированием — если во входящих `fields` есть ключ с сырым значением `null` и поле в структуре НЕ указатель, PUT отклоняется с `ErrInvalidSettingPayload` (400) ещё до мёржа/записи. Указательные поля (`height`, `chartRangeStart` и т.п.) по-прежнему свободно принимают `null`. Новые тесты `TestPutRejectsNullForNonPointerField`/`TestPutAllowsNullForPointerField`. `go build`/`go vet`/`go test ./...` зелёные.
