# Именованный тип статистики вместо позиционного тюпла

Парный документ: `megaapp-front/plans/19-food-stats-named-type.implementation-plan.md`. Оба деплоятся вместе — намеренный breaking change по решению пользователя (2026-08-02), совместимость на переходный период не поддерживаем.

## Что делаем и зачем

`GetStats` и всё, что от него зависит, гоняют статистику по дню как `[5]any`: `[вес, средний_вес, потреблённые_ккал, целевые_ккал, признак_виртуального_дня]`. Смысл каждого элемента виден только по числу-индексу в коде, который его читает. Меняем на структуру с именованными полями — и в самом хранилище/кэше на бэке, и в JSON-ответе, и во внутренних функциях, которые сейчас читают `stat[1]`/`stat[3]`.

**Решение пользователя: без обратной совместимости.** Раскатываем бэк и фронт одновременно, старый формат не поддерживаем ни на приём, ни на отдачу.

## Текущая реализация (обзор)

Тюпл `[5]any` — не только форма ответа `/api/food/stats`, это внутренняя рабочая структура, используемая в трёх местах:
- `internal/food/service.go`, `GetStats` — строит и кэширует `map[string][5]any` (индексы: `0` вес, `1` скользящее среднее веса, `2` потреблённые ккал, `3` целевые ккал, `4` признак виртуального дня).
- `internal/food/stats_cache.go`, `StatsCache` — серверный in-memory кэш по userID, хранит тот же тип.
- `internal/food/service.go`, `buildTargetKcalsForRange` (читает `stat[3]`) и `calculateTargetNutrientsForRange` (читает `stat[1]`) — используются не только для ответа `/stats`, но и внутри `GetDiaryFullUpdate` для расчёта целевых калорий/нутриентов дня в ответе дневника. То есть это не изолированный от дневника кусок — правка задевает оба пути чтения.
- `internal/food/http.go`, `GetStats` — отдаёт `map[string][5]any` как есть, без обёртки, JSON-объект вида `{"2026-08-01": [75.2, 75.4, 1850, 2000, false], ...}`.

**Побочная находка**: признак виртуального дня (индекс `4`) в `GetStats` всегда жёстко `false` — нигде в `internal/food` не найдено места, которое выставляло бы его в `true`. Похоже на мёртвое поле (возможно, задел под фичу, которая не была реализована, или осталась от старого JS-бэкенда). Не расследовал глубже — не в рамках этой задачи, просто перенести как есть под новым именем, разбираться отдельно если понадобится.

## Направление

- Именованная структура (например `DayStats` — точное имя выбрать по вкусу при реализации) с полями: вес, скользящее среднее веса, потреблённые ккал, целевые ккал, признак виртуального дня — вместо `[5]any` везде по списку выше.
- JSON-теги — обычные именованные ключи объекта, не массив. Ответ `/api/food/stats` меняет форму: было `{"дата": [числа...]}`, станет `{"дата": {"weight": ..., "consumedKcal": ..., ...}}` (точные имена ключей — на усмотрение реализации, зеркалить с фронтовым типом).
- `buildTargetKcalsForRange`/`calculateTargetNutrientsForRange` переходят на чтение именованных полей вместо `stat[3]`/`stat[1]`.

## Область охвата

- `internal/food/service.go`, `stats_cache.go`, `http.go`.
- Не входит: сам расчёт статистики (`prepareWeights`, `calculateCenteredAverage`, резолвер персональных ккал и т.д.) — логика не меняется, меняется только форма, в которой результат хранится/передаётся.

## Затронутые флоу

| Флоу | Сейчас | После |
|---|---|---|
| `GET /api/food/stats` | Отдаёт объект с массивами-значениями по дате | Отдаёт объект с именованными полями по дате — **breaking change формата ответа**, требует одновременного фронта |
| Расчёт целевых ккал/нутриентов в `GET /api/food/diary-full-update` | Читает тот же тюпл через `buildTargetKcalsForRange`/`calculateTargetNutrientsForRange` | Внутренняя правка, сам ответ дневника (уже именованный `DayNutrients`) не меняется |
| Серверный кэш статистики (`StatsCache`) | Хранит `[5]any` | Хранит именованную структуру, поведение кэша (TTL/инвалидация) не меняется |
