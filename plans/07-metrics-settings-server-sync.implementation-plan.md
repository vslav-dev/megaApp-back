# 07. Синхронизация настроек метрик с бэком

## Как сейчас

Настройки страницы метрик (выбранный сервис, размеры карточек, гранулярность, синхронизация курсора, выбор метрик на дашборде, пороги severity) живут только в localStorage браузера. Между вкладками/браузерами/устройствами не синхронизируются — есть только на той машине, где их меняли.

Для сравнения: общие настройки пользователя (тема, разделы, рост) уже синхронизируются с бэком — каждое изменение сразу летит на сервер через очередь с ретраями, оптимистично обновляя UI до получения ответа.

## Как должно быть

- Настройки метрик хранятся и на бэке (одна строка на пользователя), и в localStorage как мгновенный локальный кэш.
- **Сохранение:** изменения не отправляются сразу. После каждого изменения настройки запускается/перезапускается таймер на 5 секунд. Если за эти 5 секунд пришло новое изменение — таймер стартует заново. Как только пользователь 5 секунд ничего не трогал — собирается полное текущее состояние настроек, все элементы управления настройками блокируются (недоступны для изменения), и это состояние целиком отправляется на сервер.
- **Ответ сервера:**
  - успех — элементы разблокируются, состояние остаётся как есть (оно уже подтверждено сервером).
  - ошибка — состояние откатывается к последнему подтверждённому (последний раз, когда сервер ответил успехом — либо при загрузке, либо при предыдущем сохранении), элементы разблокируются.
- Никакого оптимистичного предположения «сервер точно сохранит» на время самой отправки — на этот момент UI заблокирован, итог известен только из ответа.
- **Загрузка страницы:** сначала мгновенно показываем то, что лежит в localStorage (для отсутствия задержки UI). Параллельно идёт запрос на сервер. Когда ответ приходит — состояние и localStorage безусловно перезаписываются тем, что прислал сервер, без каких-либо сравнений и проверок (если значения совпали — UI просто не дёрнется).
- Так гарантируется, что после обновления вкладки в любом браузере подтягиваются актуальные серверные настройки.

## Что меняем

**Бэк:**
- Новая миграция: в существующую таблицу настроек добавляется ещё одна колонка под настройки метрик — без отдельной таблицы. Таблица и так хранится по одной строке на пользователя, и она уже единственное место, где живут пользовательские настройки — лишняя таблица здесь не нужна. Значение в колонке — то же самое полное состояние настроек метрик целиком (так как часть полей — это словари с динамическими ключами сервисов/метрик, под обычные колонки они не ложатся).
- Бэк не пытается понимать структуру этого значения — он не парсит его на отдельные поля, не описывает их Go-структурой. Просто проверяет, что это синтаксически корректный JSON, и хранит/отдаёт как есть. Это убирает необходимость держать на бэке копию формы настроек метрик и обновлять её при каждом изменении состава настроек на фронте.
- В существующем модуле настроек (тот же файл/пакет, что и для общих настроек) — два новых метода: получить значение колонки по пользователю (с пустым значением по умолчанию, если строки ещё нет) и полностью перезаписать колонку. Переиспользуется тот же приём upsert «обновить, и если не задело ни одной строки — вставить», что уже используется для общих настроек.
- Новый небольшой роут (отдельный путь от общих настроек, чтобы не путать с дёрганьем общих настроек по одному полю) — получить / полностью перезаписать. Никакого нового модуля/пакета не создаётся, всё в рамках существующего.

**Фронт:**
- Сервис настроек метрик: вместо прямой синхронной записи в localStorage при каждом изменении — добавляется debounce-таймер на 5 секунд, флаг блокировки, и хранение «последнего подтверждённого состояния» для отката.
- По срабатыванию таймера: собрать текущее состояние, выставить флаг блокировки, отправить целиком на сервер; по ответу — снять блокировку и либо зафиксировать состояние как подтверждённое (успех), либо откатить к подтверждённому (ошибка).
- localStorage как и раньше пишется при каждом изменении — это лишь локальный кэш для мгновенной отрисовки, не зависит от состояния отправки на сервер.
- При инициализации страницы: чтение localStorage для мгновенного отображения, затем запрос к серверу и безусловная перезапись состояния и localStorage его ответом.
- Компонент дашборда метрик: элементы управления настройками привязываются к флагу блокировки сервиса (недоступны на время отправки).
- Очередь синхронизации с ретраями, которая используется для общих настроек, здесь не нужна — она рассчитана на частые мелкие изменения с фоновыми повторными попытками. Здесь сценарий другой: одна полная отправка после паузы, без ретраев, с явной блокировкой UI на время ожидания ответа.

## Оценка сложности

Несложно, и так даже проще предыдущего варианта с отдельной таблицей. Бэк ничего не знает о структуре настроек метрик — просто валидирует JSON и хранит/отдаёт колонку, без миграций при изменении состава настроек в будущем. Новых таблиц и новых Go-пакетов нет, только две новые колонки-метода в уже существующем модуле настроек. На фронте меняется только обвязка вокруг существующих сеттеров (добавляется таймер, флаг блокировки и снимок для отката), сама модель данных и сигналы не трогаются.
